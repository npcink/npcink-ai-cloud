# 前端 PC 开发范围与按影响选择检查 v1

Status: active. 操作者于 2026-10-26 确认。

## 1. 当前开发范围

当前 Npcink AI Cloud 项目仅做 **PC 端开发与界面验收**，适用于公共站点、
Portal、登录/注册及 Admin。移动端和平板端不在当前开发、适配、优化或
验收范围；只有操作者明确重新纳入范围后才开展相关工作。

- 不主动新增手机/平板断点、触控交互、设备矩阵或截图基线，不以这些设备的
  外观问题阻塞 PC 交付。
- 保留已有响应式代码、测试和历史证据；本决定不要求删除或禁用已有实现，
  也不授权跳过 GitHub required checks。已有整份测试附带手机用例时，可沿用
  现有执行器，不为省这一项另造工具或拆改测试框架。
- PC 窗口变窄仍属于 PC 范围。例如操作者在 1056px 宽的桌面浏览器预览，
  需要检查实际内容区和操作可达性；不能仅凭窗口宽度把它归为平板验收。
- PC 上的键盘、焦点、语义标签和可读性要求继续有效。

本文件是当前设备范围与本地前端检查选择的权威。其他活动文档中的 mobile、
tablet、390px 或“PC-first”表述不自动产生当前手机/平板开发义务；历史记录
保持原样。产品边界、安全、审计、CI 合并门禁和生产授权规则不变。

## 2. 按改动影响选择检查

开工时说明改了什么、影响哪些页面/状态、准备检查什么；完成一次连贯改动后
集中检查，不把下面各行机械叠加成每次必跑的全量矩阵。

| 改动 | 默认本地检查 | 何时扩大 |
| --- | --- | --- |
| 仅规范或说明文档 | 差异格式、受影响链接和条文一致性 | 改到实际脚本、CI 或运行配置时再走对应门禁 |
| 文案、图标、间距、列宽、按钮外观等页面局部改动 | 相关静态检查；当前页面和受影响 PC 宽度；长文本/截断/操作可达性中适用的场景 | 实际发现溢出、遮挡、行为变化或共享影响时 |
| 颜色、背景、透明度、边框、阴影、主题相关样式或逻辑 | 当前页面相关状态的明暗主题、对比度和可读性 | 共享颜色 token 或主题切换机制变化时，增加受影响页面 |
| 搜索、筛选、排序、分页、导航、表单等交互 | 对应交互和其相关成功/失败/等待/返回上下文 | 状态所有权、API、权限、保存或其他功能受到影响时 |
| 公共组件、全局样式、后台壳层、共享几何 token | 受影响消费者的代表页面/状态及相关静态检查 | 依赖范围不明确或跨多种页面模型时，扩大矩阵 |
| 认证、权限、计费、凭据、数据契约、依赖或运行环境 | 对应既有风险门禁 | 按原有工程、安全、集成和发布规则执行，不按“外观修改”减免 |

**暗色检查按影响触发。** 没有改变颜色/主题相关内容、也没有改变这些样式的
继承、作用域或显示条件时，纯文案、间距或列宽调整通常不需要重跑暗色环境。
不能只看是否修改颜色字面值：切换 class、主题容器或浮层可能间接影响暗色。
先确认影响，再选择检查；不默认乘上语言 × 主题 × 设备的全组合。

语言检查同样按影响选择：修改翻译键时检查对应语言完整性；长度、截断或换行
受影响时检查相关长文案。仅改变链接外观，不自动重跑登录、创建客户或后端
写入流程；改了交互语义或数据路径，则验证对应行为。

## 3. PC 宽度与检查节奏

- 首先检查操作者实际预览窗口和当前主题。没有指定窗口时，沿用现有 PC
  基准（Admin 为 1440×1050），不建立新的设备测试体系。
- 列宽、工具条、弹窗或断点发生变化时，补充相关的较窄 PC 窗口（例如 1280px，
  或实际报告的 1056px）；只改文案且不影响布局时，不强制扫全部宽度。
- 开发中先做最小有效检查并快速看效果；确定方向后，在一次完整改动的收尾
  集中验证。若操作者要求先自查再展示，则先完成相关检查再展示。
- 检查通过后，没有新改动、失败或未解决风险，不重复同一个检查。
  新改动只补受影响的检查；复用证据须说明来源、环境和仍适用的范围。

## 4. 定向检查与全量检查

优先使用仓库现有单元、契约和浏览器测试，选择最小的相关 spec，必要时用现有
`--grep` 选择相关用例。若一份 spec 无法安全拆选，可执行整份，不为一次外观
调整编写一套新测试。静态检查按受影响文件和现行门禁选择。

例如客户目录现有定向浏览器入口是：

```bash
pnpm --dir frontend run test:e2e tests/e2e/admin-accounts-queue-v2.spec.ts
```

`pnpm run check:admin-ui:visual` 是注册的跨页面视觉矩阵，**不是当前页面的
定向命令**。局部外观改动不默认运行全后台视觉矩阵；共享影响广或不明确、
对应阶段综合验收、PR/发布策略明确要求时，才在相应收尾运行一次。
风险分级与检查维度是两件事：减少无关主题/设备组合不意味着把 `material`
或 L2 自动降为低风险。

GitHub required checks、`check:admin-ui` 的发布要求、M4 运行身份核验和生产
授权仍遵循各自标准。自动规划器给出宽泛本地检查建议时，结合本文件记录
适用的页面/状态/主题范围；不能因此把强制 CI job 标成通过或删去既有测试。
仅规范文档变更默认不跑浏览器、应用构建或 M4 同步。

## 5. 失败与证据报告

- 先判断失败是否与本次变更有关。新出现且归因不明的失败不能直接称为旧问题。
- 已确认无关的失败单独记录命令、版本、原因和适用范围；没有相关新变化时不
  反复重跑，也不扩大当前修复范围，不以更新截图基线、放宽阈值或删测试求绿。
- 报告实际运行、通过、失败及未适用的检查，并用一句话说明选择理由。
  当前页面通过不等于全后台通过；local、CI、M4 candidate、merged、M4 accepted、
  production 与人工验收保持分开。
