## 1. 执行结论

统一头部值得做，但只能做成一个有明确终点的共享基础层。

头部承担跨页面重复且高频的四项任务：

1. 说明当前页面是什么；
2. 说明操作者正在处理哪个范围；
3. 保留一个主操作和有限次操作；
4. 用紧凑、可核实的事实说明当前状态。

这些内容适合统一。页面正文承担具体操作任务，不适合强行统一：外部服务是
服务目录，向量设置是固定配置表，运行档案是候选链目录。统一头部不等于给
三页再包一层相同卡片，也不等于建立一张万能配置表。

本阶段最终形成的边界是：

```text
共享页面身份、操作层级、事实摘要
  -> 每个非认证 ready state 使用 BackofficePageHeader
  -> 配置页兼容别名委托同一 primitive

保留任务专属正文
  -> queue / detail / configuration / diagnostic 各自使用合适工作面
  -> 不改变 API、草稿、保存、凭据、确认或最终写入所有权
```

## 3. 设计规范

### 3.1 顶层头部结构

每个非认证 Admin 页面的 ready state 使用 `BackofficePageHeader`，顺序保持：

1. eyebrow：简短说明所属操作域；
2. title：页面唯一的一级标题，可带信息提示；
3. description：一句话说明操作者任务或范围；
4. action：最多一个主操作和有限次操作；
5. summary：紧凑、事实性的当前状态。

`BackofficeConfigurationHeader` 只作为配置页兼容别名存在，并委托同一
primitive。页面内部 section 可以使用 `BackofficeLayer`，但不能制造第二个
页面标题。Loading 和 failure shell 可以保留有限重试面，但不得编造 summary。

### 3.2 摘要只表达事实

摘要项必须满足至少一个条件：影响当前判断、解释工作范围、或指出下一步。
正常状态保持安静；异常、待配置和需要处理才提高视觉权重。状态必须包含
文字，不能只依赖颜色。

运行配置页使用以下词汇：

- `Ready` / `已就绪`：运行对象当前可操作；
- `Needs config` / `待配置`：运行对象配置不完整；
- `Configuration saved` / `配置已保存`：页面草稿已持久化。

“配置已保存”不能冒充运行对象“已就绪”；“HTTP 200”也不能冒充视觉或
业务可用性验收。

### 3.3 操作层级

- 主操作只保留一个，且必须完成页面最主要的操作者任务；
- 刷新、测试、诊断入口和跨页面参考通常是次操作；
- 删除、清空、停用和恢复不进入默认主操作区；
- 没有真实主操作的只读页面不必为了版式对称制造按钮；
- 操作反馈不能导致头部和主要工作面跳动。

### 3.4 正文差异必须保留

共享头部不得反向要求页面正文同构。应按信息结构选择工作面：

| 操作者任务 | 正文形式 |
| --- | --- |
| 比较多个同构对象 | 语义数据表 |
| 编辑固定、短而稳定的配置 | 三列配置表 |
| 在多个异构设置域中切换 | 稳定目录 + 单一活动面板 |
| 检查异常和证据 | 结论 + 异常队列 + 上下文证据 |
| 处理一个具有稳定 URL 的复杂对象 | 专用详情页 |

不要为了“更统一”新增外层卡片、通用大容器、新组件库或跨领域超级设置页。

## 4. 为什么外观看似简单，交付仍然变慢

代码改动不大，但交付对象不是一张静态截图，而是共享操作界面。耗时主要
来自以下工程约束：

| 事实 | 影响 | 正确处理 |
| --- | --- | --- |
| 共享头部影响多个 page model 和大量路由 | 一个 primitive 错误会造成全 Admin 回归 | 先试点，再分批覆盖，并运行跨路由结构与视觉门禁 |
| 多个并行工作树和共享 M4 可能拥有不同 candidate | 直接覆盖会破坏他人工作或把旧候选误认成缓存 | 检查 worktree、owner、revision、dirty 和 acceptance state，失败关闭 |
| 根级 `package.json` 同时参与 CI 分类和 M4 镜像指纹 | 仅增加视觉测试入口也会触发 backend fast gate 和重新构建 | 在改动前声明 build/runtime 影响；合法门禁不能为了快而漏掉 |
| 本地 fixture、M4 路由和登录后人工页面是不同证据 | 任一证据不能代替另外两类 | 分别报告 local、candidate、merged、accepted、human acceptance |
| 临时 M4 浏览器隧道可能超时 | 页面日志可见 `200`，但浏览器仍拿不到完整响应 | 停止超时链路，保留本地确定性视觉证据，并明确人工验收缺口 |
| 共享改动进入受保护 master | push 不等于完成 | 等待 CI、合并，再从干净 current master promote |

真正需要改进的不是删除这些安全边界，而是更早识别风险档位，避免在已经
得到视觉结论后继续做无收益的微调或重复运行同一全量门禁。

## 5. 轻量实施流程

### 5.1 先分类，不先写 CSS

| 风险档位 | 例子 | 最小本地验证 |
| --- | --- | --- |
| low | 文案、标签或状态词，不改变几何和交互 | 聚焦 contract/type/lint；若进入既有视觉 spec，运行对应 spec |
| material | 单路由头部结构、操作层级或摘要布局变化 | `check:admin-ui` + 目标路由确定性 PC 浏览器证据 |
| shared | 共享头部 primitive、跨路由覆盖或几何 token 变化 | `check:admin-ui` + 完整 `check:admin-ui:visual` |

如果修改根级依赖、锁文件、Docker、Compose、部署脚本或参与镜像指纹的输入，
立即按 build/runtime lane 处理。不要先尝试 source-only 流程，再在失败后才
重新分类。应用源码的 candidate dispatch、合并后 promotion 和 M4 证据仍按
M4 标准与当前任务授权执行；本表只按视觉风险裁剪本地门禁，不豁免运行预览。

### 5.2 推荐顺序

```text
声明 page model、operator job、动作层级和非目标
  -> 检查一个真实参考页和目标长文本状态
  -> 只改共享头部或一个明确路由批次
  -> 运行最窄结构/类型/浏览器门禁
  -> 风险为 shared 时运行完整 Admin 视觉门禁
  -> coherent checkpoint 后部署 M4 candidate
  -> 发布受保护 PR，等待 required checks
  -> 合并后从干净 current master promote
  -> 单独记录 human visual acceptance
```

### 5.3 视觉证据要求

- 使用 `frontend/admin-ui-manifest.json` 的 `1440x1050` PC 视口；
- fixture 必须覆盖足够长的中文、状态和操作，不能依赖本地真实数据数量；
- 验证唯一页面标题、无横向溢出、首屏工作面、单一主操作和文字状态；
- 截图附件是证据，不进入源码提交；
- 远端受登录保护时，不读取或索要密钥，不把登录页当成页面视觉证据；
- 失败或超时必须记为未完成，不能降低断言来获得绿色结果。

## 6. 停止条件

同时满足以下条件后，停止继续打磨：

- 所有非认证 ready state 使用已接受的共享头部；
- 每页只有一个顶层标题；
- 页面主操作层级和事实摘要可直接理解；
- 目标正文工作流、API、草稿、凭据和确认行为未改变；
- 结构、类型和相应视觉门禁通过；
- 用户已确认方向，且没有新的硬门禁失败或真实操作阻力。

以下理由不足以继续扩张：

- “还能更漂亮一点”；
- “顺便把所有正文也统一”；
- “为了清零清单再迁移一个低频页面”；
- “既然改了头部，不如引入完整组件库”；
- “M4 已返回 200，所以可以跳过必要的行为或人工证据”。

### 发现的问题

| 严重程度 | 问题描述 | 根本原因 | 改进建议 |
| --- | --- | --- | --- |
| 必须改正 | 用户一度无法看到页面，早期交付状态与可验收入口没有同步说清 | 把源代码完成、candidate 部署和用户可见页面混在同一叙述中 | 每次更新同时报告 revision、URL/路由、authentication、candidate/accepted 和 human acceptance |
| 应当改正 | 一个外观任务经历多轮“建议—落实—再建议”，总历时与视觉改动不成比例 | 没有在第一次认可后立即冻结视觉目标和停止条件 | 用户确认效果后只收口硬门禁、证据和文档；新的美化建议进入下一批，不继续叠加 |
| 应当改正 | 修改根级 `package.json` 后，直到 M4 frontend slot 指纹失败才按 build/runtime 重新分类 | 变更前只按“无依赖变化”判断，没有检查指纹输入范围 | 修改根级命令前先检查 dependency/image fingerprint；预先选择 deploy lane |
| 应当改正 | M4 浏览器隧道长时间无输出后才终止 | 浏览器启动器缓冲输出，且没有预设远端页面超时预算 | 远端视觉链路设定明确时间预算；超时后停止、查日志和路由，不重复等待或降低断言 |
| 建议改进 | 共享头部迁移牵动大量旧 contract 文本断言 | 部分测试约束物理结构而非用户行为 | 继续保留架构禁令，但让行为测试围绕标题、操作层级、摘要和工作面，而非旧组件名称 |

### 做得好的地方

- 先在配置页试点，再扩展到其余页面，没有一次性重写全 Admin；
- 复用 `BackofficePageHeader` 并保留兼容别名，没有引入新组件库；
- 没有借视觉统一改变 API、凭据、保存事务或 Cloud/WordPress 边界；
- 保护并行工作树，精确暂存，没有 reset、stash 或覆盖共享 candidate；
- 本地、CI、M4 candidate、merged master、M4 accepted 和人工验收始终分开；
- M4 隧道超时后没有把日志中的 `200` 包装成登录后视觉验收；
- 用户指出“只是样式为什么慢”后，查明了根级命令、CI 分类和镜像指纹的具体成本。

### 下次重点关注

1. 在第一次实现前写出风险档位、用户验收入口和停止条件；
2. 用户确认视觉方向后冻结外观，只完成硬门禁和交付链；
3. 根级 `package.json`、锁文件或部署输入变化要在 M4 前预判重建；
4. 远端浏览器链路使用时间预算，并把登录后人工接受保持为独立状态；
5. 只在真实操作阻力出现时继续迁移正文，不进行无目标的全站美化。

## 8. 后续策略

统一头部阶段至此冻结。后续 Admin 工作应回到操作者问题，而不是继续寻找
视觉统一项目：

1. 新页面默认复用现有头部和页面模型；
2. 旧页面只在真实任务阻力或硬门禁失败时修复；
3. 共享头部若没有新增职责，不再增加 props、布局模式或状态词；
4. 产品资源优先投入 README 当前锁定的核心 AI 用户链路；
5. 人工在 M4 登录后确认页面可见性时，只补充 human acceptance 证据，
   不重新开启样式迭代。
