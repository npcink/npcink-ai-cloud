# Codex 并行开发流程工作记录（2026-08-01）

状态：工作记录，未形成新的强制决策。

目的：记录多会话并行开发遇到的效率问题、已经落实的改进、仍然存在的使用负担，以及后续可选方向。本文不是发布、M4 接受或生产就绪证据。

## 1. 使用背景

当前主要通过 AI 会话开发项目，可能同时打开 3 到 5 个会话，分别处理项目的不同部分。期望是提高调查、实现和验证速度，而不是让使用者承担更多 Git、PR、M4 或任务调度工作。

实际暴露的问题包括：

- 每个顶层会话都倾向于执行完整的调查、实现、测试、PR、CI 和 M4 流程；
- 多个会话会重复检查仓库、等待 CI、追赶变化中的 `master`；
- PR、受保护合并通道和共享 M4 本质上仍是串行资源；
- 会话越多，所有权确认、worktree、交接和状态解释的成本越高；
- 把 Builder、Integrator、`local-ready` 等术语直接交给使用者管理，虽然安全，但日常操作仍然过于麻烦。

目标不是最大化同时写代码的会话数量，而是在不损坏证据链的前提下减少等待和重复劳动。

## 2. 已经落实并合并的改进

### 2.1 并行协作底线

PR `#443` 已合并，建立了以下仓库协作底线：

- 一个冲突域只有一个实现 owner；
- 同一时间只有一条人工变更进入受保护合并通道；
- 同一时间只有一个共享 M4 操作 owner；
- 并行 Builder 可以在干净提交和窄门禁完成后停在 `local-ready`；
- Integrator 负责基线刷新、PR、CI、合并和 M4；
- 等待进入合并通道的 ready 项默认不超过两个。

这些规则解决的是来源、合并和运行时证据互相覆盖的问题。它们是安全底线，不应该成为使用者每次都要手工填写的流程表。

### 2.2 前端专属 CI 快速通道

PR `#444` 已合并，增加了 fail-closed 的 `frontend_only` 分类：

- 只有全部变更都位于 `frontend/**` 时才进入前端专属通道；
- 该通道跳过 Python 依赖审计和 targeted backend 门禁；
- required `backend` 聚合检查仍然存在，并验证后端作业是按预期跳过；
- 混入 lockfile、workflow、脚本、文档或后端文件时，自动回退原有门禁。

这项改进消除了纯前端改动等待无关后端检查的结构性原因。真实纯前端 PR 的 hosted runner 总耗时尚未获得自然样本，因此当前仍标记为 `未测量`。

## 4. 为什么 skill 方案仍然显得麻烦

skill 可以隐藏一部分流程，但不能消除以下事实：

1. 如果使用者仍然创建 3 到 5 个独立顶层会话，这些会话之间没有天然的单一总控上下文；
2. skill 需要进入目标分支并在新任务中加载，首次落地仍有配置和交付成本；
3. 显式输入 `$npcink-parallel-delivery` 仍然是额外操作；
4. custom agents 能降低主任务的上下文噪声，但 PR、CI、M4 仍然必须串行；
5. 过度固定角色和收据会把内部协调细节暴露给使用者；
6. hooks 或额外队列服务虽然可以做机械约束，却会引入新的信任、维护和故障面。

因此，skill 只能作为内部实现方式，不应成为新的用户流程负担。

## 5. 更简化的目标体验

理想交互应当是：

```text
用户：系统性检查并修复这个页面。

Codex 主任务内部自行决定：
1. 是否值得并行；
2. 并行哪些只读调查；
3. 是否需要一个实现 worker；
4. 何时进入 PR、CI 和 M4；
5. 最后只向用户报告结果、风险和未测量项。
```

使用者不需要：

- 创建或命名 Builder、Integrator；
- 维护 ready 队列；
- 填写 `local-ready` 收据；
- 决定哪个会话操作 M4；
- 每次显式输入 skill 名称；
- 阅读子 agent 的中间日志。

## 6. 可选方向

### 方向 A：一个主任务自动使用 subagents

保留一个顶层任务，由主任务按需要生成最多三个 subagents。优先并行只读探索、浏览器证据、日志分析和独立复核；写入阶段最多一个 writer。

优点：用户操作最少，Git、PR、CI 和 M4 天然只有一个 owner，主任务上下文也更干净。

限制：需要 Codex 在合适任务中自动触发项目 skill 或遵循项目指令；复杂任务仍受串行交付资源限制。

### 方向 B：保留多个顶层会话，但只做本地模块实现

3 到 5 个会话分别处理真正独立的模块，全部停在本地提交；另设一个 Integrator 会话统一交付。

优点：适合多个明确独立功能。

限制：使用者仍需理解任务边界和 Integrator，操作负担没有完全消失。

### 方向 C：只并行调查，不并行写入

所有代码写入由主任务完成，subagents 只负责调查、复现、浏览器和 review。

优点：冲突最少，适合 Admin 页面、共享 primitives、CI 和 M4 等高冲突工作。

限制：大型独立实现无法充分利用并行写入。

### 方向 D：暂停 skill 原型

保留已合并的协作底线和前端 CI 优化，不继续合并 custom agents/skill，等真实使用模式更加稳定后再决定。

优点：没有新配置和维护面。

限制：仍需要在每个任务中临时提示 Codex 如何使用 subagents。

## 7. 当前建议与未决事项

当前建议偏向方向 A，但不把它视为已经接受的决定：

- 用户只描述任务，不管理并行流程；
- 主任务自行判断是否需要 subagents；
- 默认并行只读工作，写入保持单 owner；
- skill 即使保留，也应允许隐式触发，不要求用户输入 `$skill`；
- 暂不引入 hooks、后台守护进程、队列数据库或新的部署控制面；
- 用未来几次真实任务测量总耗时、用户等待时间、冲突次数和重复 CI 次数，再决定是否合并或调整原型。

仍需决定：

1. 是否继续把当前 skill 原型送入合并通道；
2. 是否只保留 custom agents 而不要求显式 skill；
3. 是否在项目规则中允许复杂任务自动生成 subagents；
4. 多会话并行是否仅用于真正独立的仓库或模块；
5. 用什么自然任务作为首次效果测量，避免为验证而制造无意义 PR。
