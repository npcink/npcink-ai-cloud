# Portal 生产邮箱与真实写作闭环验收步骤 — 2026-10-16

Status: operator-executed validation checklist; not production deployment
authorization, not a general availability approval, and not a substitute for
the canonical release checklist.

2026-10-17 更新：原文件从本地提交 `867ebcb4` 恢复。#1116 和 #1118 已有
成功部署工作流；不要因旧清单的候选字样重复部署 `982b132d`。现行分工为：
操作者在生产验证收件、登录、站点连接、人工采用与保存；开发侧核对版本、
预算合同、run/用量/原生反馈和失败根因。没有原始证据时记录待核实。
历史与最新进展见[三会话综合纪要](history/portal/2026/portal-three-session-synthesis-and-next-stage-2026-10-17.md)。

目的：由开发侧准备可执行的验证顺序，由操作者在实际生产环境完成真实邮箱、
真实站点和一次受控写作闭环。操作者只需输入自己的邮箱验证码、站点信息和受
保护的生产凭据；不要把密码、验证码、Provider key、Cookie、完整文章正文或
`.env.deploy` 发回会话。

本清单默认生产入口为 `https://cloud.npc.ink`。如果当前正式 Portal 地址不同，
以生产 `/admin/service-settings` 中已保存的 Portal public URL 为准。

## 0. 开始前的三个前置条件

在打开 Portal 之前，先确认：

1. **验证环境已确认**：开发侧核对最新部署回执，操作者使用正式入口测试。
   2026-10-17 查得最近成功部署工作流绑定 `2af00741`；本清单不要求操作者
   理解 Git 或从服务器提取 SHA，开发侧另行保存该证据。
2. **SMTP 已配置**：在 `/admin/service-settings` 确认 SMTP host、port、TLS、
   sender 和密码已保存；本次使用一个你能访问的测试收件箱。
3. **Provider 预算已覆盖**：若要做真实写作，先配置 `provider_account_spend_budget`
   的 Provider 分类、日上限和月上限；开发侧以确定性证据核对保护已启用、
   覆盖关系与缺配置拒绝逻辑，不在生产制造超支或缺配置调用。没有预算覆盖、
   没有允许使用的 Provider，或当前生产阶段明确关闭付费 Provider 时，只做邮箱和
   账户/站点验收，停在第 3 节，不重复尝试生成。

不要用历史演示账户作为新 Free 账户验收样本。历史余额、站点数量和容量可能已经
偏离当前 Free 规则。

## 1. 邮箱注册与 Free 权益

使用一个从未注册过的测试邮箱：

1. 打开 `https://cloud.npc.ink/portal/register`。
2. 输入测试邮箱，点击“发送验证码”。只点击一次，等待邮件。
3. 在收件箱确认发件人、主题和验证码；记录发送时间和收到时间，不保存验证码
   到报告中。
4. 在 Portal 输入验证码并完成注册。
5. 进入 `/portal`，确认页面显示账户级 Free 信息、当前周期额度和“连接第一个
   站点”的下一步。按当前阶段计划核对预期：300 AI credits、30 天周期、尚无
   连接站点；若生产配置展示不同数值，记录实际值，不要自行修改数据库或重置
   账户。

通过条件：

- 邮件在生产收件箱中真实到达；
- 验证成功后进入 Portal，而不是开发入口或错误页面；
- 只创建一个账户级 Free 权益；
- 页面没有把未连接站点误报为异常，也没有显示内部 Provider、token 或成本信息。

## 2. 退出后再次登录

1. 从 Portal 退出。
2. 打开 `https://cloud.npc.ink/portal/login`。
3. 使用同一个邮箱请求新的验证码，收件后完成登录。
4. 回到 `/portal`，确认仍是同一个账户，Free 周期和剩余额度没有重复创建或被
   重置。

通过条件：登录成功、账户上下文保持一致、没有因为重新登录生成第二份 Free 或
   丢失账户状态。

如果邮件未到达，不要连续请求多个验证码。记录时间、邮箱域名、页面提示和是否
   在 SMTP 服务端看到投递，再停下来排查 SMTP 或域名配置。

## 3. 绑定一个真实 WordPress 站点

准备一个可回滚的测试站点和当前生产 Addon：

1. 在 WordPress 站点的 Npcink Cloud Addon 中开始连接流程。
2. 按 Addon 跳转到 Portal，使用刚才的测试账户登录。
3. 在 Portal 的账户选择/连接确认界面明确选择目标账户，再确认绑定；不要把站
   点绑定到历史演示账户。
4. 返回 WordPress，确认一次性连接流程完成；不要复制或保存浏览器返回的临时
   exchange code。
5. 回到 `/portal`，确认站点出现在站点列表，状态为已接入或等价的生命周期状态。
6. 打开站点详情，确认站点 URL、名称、连接状态和服务状态属于同一站点；不要把
   “服务状态未知/需关注”误当成“连接失败”。

通过条件：站点只出现在被选账户下，连接成功后能回到 WordPress，Portal 不显示
签名密钥、Provider ID 或内部诊断字段。

## 4. 真实写作闭环（只做一次最小任务）

只有第 0 节预算条件满足后才执行。使用一篇非敏感的测试文章或测试草稿，不要
上传客户隐私、密钥、订单信息或未公开内容。

1. 在 WordPress 编辑器打开测试草稿，确认站点和当前 Cloud 连接是刚才绑定的站点。
2. 使用当前已支持的官方 WordPress AI 入口，发起一次最小写作任务。优先做一
   次标题建议或短段落建议，不要在第一次验证中批量生成、重复点击或同时打开
   Site Knowledge 等额外变量。
3. 记录开始时间、结束时间、页面显示的成功/失败状态和是否出现重试。不要把
   完整提示词或生成正文发回会话。
4. 等待建议返回，确认未点击采用/插入前，结果不会自动替换编辑器字段。
   阅读、修改后明确采用到草稿。WordPress 自动保存可能保存已采用的草稿，
   它与 AI 未经确认写入不同；测试保持草稿，不点击发布。
5. 明确点击保存草稿，确认保存完成。
6. 重新加载编辑器，确认人工采用的标题或正文保留、文章仍为草稿。
7. 操作者查看 Portal 前后积分和操作结果即可；开发侧再核对对应 run、
   成功/失败、耗时及实际 Provider/模型，不要求操作者自行分析内部日志。
8. 开发侧核对自然产生的 `agent.feedback` 与本次 run 的关联、去重和隐私。
   区分尚未投递、无权限查询与确实缺失；不手动制造或强制清空队列。
   保存成功、journey 事件或模拟事件均不能替代原生反馈。

通过条件：

- 真实 WordPress 请求成功完成一次；
- Cloud 有对应 run 和用量证据；
- credits、Provider 成本和预算预留可以对应到这一次调用；
- AI 结果只有经人工采用才进入编辑器，显式保存后可回读；
- 反馈事件（若已启用）能用同一 `source_run_id` 关联、去重且不含正文/提示词；
- 文章保持草稿状态，除非你明确选择发布。

一次成功是首条 smoke，不能关闭[六条链路清单](wordpress-ai-loop-verification-checklist-2026-09-22.md)
中“不少于 10 次真实使用”等尚未满足的要求。后续按自然写作积累，不为凑数重复调用。

## 5. 任一步失败时的停线规则

出现以下任一情况，停止后续真实调用和用户邀请，只保留一次失败证据：

- 验证码邮件持续不到达、验证码失效逻辑异常或登录进入错误账户；
- 新注册账户重复获得 Free、额度不符合当前配置或站点跨账户可见；
- Addon 连接成功但 Portal/WordPress 返回状态不一致；
- Provider 预算缺失、超限未拒绝、重复点击产生重复扣费或调用；
- AI 建议在人工确认前自动写入 WordPress；
- Cloud 没有 run/用量证据，或实际命中的 Provider 无法确认；
- `agent.feedback` 事件带出正文、提示词、邮箱、凭据，或无法与 run 去重关联。

不要通过重复点击、重发验证码、重复生成或清空账户数据来“把结果跑绿”。先保留
时间、页面、操作和可见提示交回开发侧定位；HTTP 状态和内部引用由开发侧补查。
缺少内部引用本身不是要求用户重新生成的理由。

## 6. 请回传的最小结果

操作者只需反馈收件/登录、Free 显示、站点连接、生成/采用/草稿保存是否成功，
以及时间和一个卡点。下表同时是开发侧补证据的工作表，不要求操作者填写内部字段。
不要回传密码、验证码、密钥、Cookie 或文章正文：

| 项目 | 结果 |
| --- | --- |
| 实际生产 SHA | 完整 SHA 或部署系统显示的 revision |
| Portal 地址 | 公网地址 |
| 邮箱注册 | 收到/未收到；验证成功/失败；发送与收到时间 |
| Free 权益 | 套餐、周期、额度、站点数（按页面实际值） |
| 再次登录 | 成功/失败；是否保持同一账户 |
| WordPress 绑定 | 成功/失败；站点状态 |
| 真实写作 | 成功/失败；开始/结束时间；是否人工保存 |
| Cloud 证据 | run/usage 是否出现；credits 是否变化；Provider/模型脱敏名称 |
| 反馈证据 | `agent.feedback` 已收到/未收到/无法核对；关联引用可脱敏 |
| 主要阻碍 | 一句话描述；附脱敏错误类别或 trace/run 引用 |

## 7. 开发侧收到结果后的处理

我会按以下顺序判断，不把所有失败都归因于 Portal UI：

1. 先区分部署版本、SMTP、账户/站点授权、Provider、WordPress Addon、观测链路；
2. 用你提供的时间和脱敏引用对照当前代码合同与日志字段；
3. 只修复实际阻塞的最小拥有者模块，并补对应回归测试；
4. 重新走当前 `master`、PR、M4/生产门禁，不直接在服务器改应用代码；
5. 真实用户试用只有在邮箱、连接、真实写作和预算边界全部通过后才开始。
