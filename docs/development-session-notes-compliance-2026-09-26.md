## 2. 合规/法律类工作底稿的方法（本次主要沉淀）

- **四列结构**：问题 / 初步理解（附来源）/ 需操作者确认的点 / 对产品的影响
  面，配合 `☐`/`☑` 生命周期（勾选权留给操作者）。所有法律定性只出现在
  "需确认"列，AI 会话整理不裁决。
- **"非法律意见"声明放显著位置**（标题下引用块），并在声明里写清使用
  方式——防止工作底稿被当成结论引用。
- **来源分级**：法规原文（核验过全文的才给深层 URL）> 政府网站（核验不到
  深层 URL 时只标机构站点、不构造链接）> 律所/云厂商解读（仅作理解参考，
  单独分组列出）。每条来源标检索日期；正文引用用编号回指来源清单。
- **修订不改原判断**：分阶段修订只新增章节与重编号，v1 的四方向条目原文
  保留，修订记录写明改了什么；交叉引用（"见第 X 节"）在重编号后必须逐个
  核对——本次靠 grep 找回两处漏改。
- **触发线分离**：把"公开注册（公众线）"与"收费（经营性线）"拆成两条独立
  触发线，把每项合规义务挂到四级验证阶段（邀请制免费 → 邀请制收费 →
  公开免费 → 公开收费）上，"每升一级只付一级的合规成本"。这个思路可复用
  于其他"先验证后合规/先验证后投入"的决策，也把大而全的合规清单变成了
  跟产品排期挂钩的执行顺序。

## 3. 先查存量再回答（避免让人重做已有的事）

回答"服务协议做好了吗"这类事实问题前，先搜仓库再开口：本仓 `site/terms/`
已有中英三页法律文件（服务条款/隐私/数据保留），Portal 注册页已有"继续即
同意"挂钩，观测同意有独立标准文档。先盘点存量、只谈缺口（本次缺口仅：
AI 标识章节、举报入口、免费额度条款），比建议"从零做协议"准确得多。
