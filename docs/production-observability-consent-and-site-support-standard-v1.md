# 正式用户观测授权与站点支持规范 v1

状态：已接受，适用于正式用户邀请前的开发收尾和后续迭代。

## 1. 目标

在不增加正式用户操作、不建立第二套站点身份系统、不采集客户行为画像的前提下，
让运营人员可以根据站点信息和匿名运行证据快速排查工单，并让产品团队持续改进功能。

## 2. 已接受的边界

| 概念 | 唯一职责 | 负责人 |
| --- | --- | --- |
| `site_id` | 永久识别哪个正式站点 | Cloud 认证/现有 Site 模型 |
| `Site.name` | 工单和运营页面中的可读站点名称 | Cloud `Site` |
| `Site.site_url` | 站点定位的辅助信息 | Cloud `Site` |
| monitoring | 站点管理员是否授权匿名运行/故障诊断数据 | WordPress Addon |
| `cohort` | 未来显式实验或研究分组，可为空 | 具体实验合同 |

普通正式用户流程不要求 `cohort`，不把正式用户称为“测试用户”，也不把 `cohort`
当作站点身份、客户身份或永久标签。

Cloud 只负责运行时、观测和只读详情；Addon/WordPress 仍拥有授权、采集同意、
本地控制面和最终写入真源。

## 3. 用户流程

1. 管理员完成 Cloud 连接并通过验证。
2. 验证完成后的明确确认框询问是否允许匿名诊断。
3. 允许后，复用现有 monitoring 权限和传输路径；拒绝则保持关闭。
4. 正式用户继续正常使用，不需要看设置页、打开 monitoring 或填写 cohort。
5. 之后管理员仍可从现有权限设置修改选择。

确认框不能触发额外 Cloud 请求，不能创建队列、注册表或新的采集路径。

## 4. Cloud 观测展示规则

站点级观测摘要必须同时保留：

- `site_id`：稳定技术定位值，错误列表和工单引用不得删除；
- `site_name`：优先展示的可读名称；
- `site_url`：低频辅助信息，可截断展示；
- 观测统计和健康状态。

观测汇总通过现有 `Site` 表只读投影名称和 URL，不把站点详情复制进每条 Addon 事件。
若历史事件没有对应 Site 记录，仍返回 `site_id`，名称和 URL 为空，不能丢弃统计。

## 5. 分阶段交付

### 阶段 1：连接后同意

目标：把管理员唯一必要动作放在连接验证完成后的明确确认框中。

验收：允许/拒绝都可重复验证；无同意不发送 monitoring；确认框不产生额外 Cloud HTTP。

### 阶段 2：站点支持摘要

目标：支持人员能用站点名称快速识别客户，同时保留 `site_id` 进行稳定排查。

验收：跨站点不串数据；站点过滤有效；缺失 Site 记录不导致观测汇总失败。

### 阶段 3：本地包和人工安装

目标：在正式服务器人工安装前，确认精确 ZIP 可激活、可回滚、包内容完整。

验收：PHP/行为/边界测试、Playground、发行清单、ZIP 完整性和 Plugin Check 全部通过。

## 6. 验证和发布纪律

验证顺序采用“最窄、最便宜、最接近风险”的梯度：

1. 变更文件级测试和静态检查；
2. 管理员 UI 类型、lint、结构门和必要的浏览器门；
3. Cloud 变更使用 M4 候选同步及 focused 测试；
4. Addon 使用 Playground 和精确发行 ZIP 验证；
5. 只有用户明确授权时才进入 PR、合并、Release 或生产部署。

本阶段最多 12 次真实 Provider 调用；本方案不需要真实 Provider 调用。
本地 Fake Provider 与正式用户数据必须隔离。

## 7. 已知问题与停止条件

- Admin 全量视觉门中与本路由无关的历史基线失败必须保留证据，不得借机扩大范围。
- 第二个独立阻塞出现后，停止扩展当前阶段，另开后续任务。
- 两次相同外部传输失败后停止自动重试，转入恢复流程。
- 不因“方便分析”新增 `site_ref`、第二注册表、第二队列、客户画像或 cohort 强制字段。

## 8. 后续数据使用建议

默认只收集匿名、元数据级运行证据：成功/失败、错误码、延迟、插件版本、时间和
站点技术标识。禁止 prompt、生成文本、用户身份、凭据、原始内容和原始事件 payload。
任何新增字段都必须说明用途、保留期限、同意条件和删除/停用行为。
