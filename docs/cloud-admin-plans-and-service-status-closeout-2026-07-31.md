## 1. 阶段结论

这轮工作的最终价值不是把两个页面“做得更漂亮”，而是把内部 Admin
界面重新约束为高效操作台：

- 套餐目录负责比较套餐、查看活跃订阅并进入一个统一维护工作台；
- 服务状态负责找出受影响客户、理解问题和影响，并从同一张表进入处理路径；
- 高频判断事实留在表格或默认编辑面，内部 ID、诊断标识和低频证据退到详情；
- 同一对象不再同时提供整行跳转、重复按钮和重复检查器入口；
- 正常状态不制造动作，警告和错误才显示与原因对应的处理入口；
- URL 拥有可分享的筛选状态，临时选中状态不再冒充业务真值；
- UI 收缩不自动授权删除后端商业、审计或运行时能力。

适用于后续 Admin 页的最短判断链是：

```text
找到对象 -> 判断状态和影响 -> 执行唯一合理动作 -> 得到可信结果 -> 回到原队列
```

任何常驻内容或操作，如果不能缩短这条链，就应被删除、降级到低频披露，
或迁移到对象详情。

## 3. 从套餐目录得到的产品经验

### 3.1 目录和编辑器必须分工

目录是比较面，不是完整详情页。它只承载一眼能比较的商业参数和两个明确入口：

- 活跃订阅数量：回答“谁在使用”；
- 管理：回答“如何修改这个套餐”。

参数说明、默认值、诊断信息和保存循环属于统一工作台。套餐 ID、版本号和
原始 JSON 不应因为“后端有这个字段”就常驻目录。

### 3.2 统一维护入口比多层详情路由更高效

当对象数量固定、编辑字段结构一致且不需要深链接协作时，列表加共享工作台
比“列表 -> 详情 -> 编辑 -> 高级页”更短。独立 `/admin/plans/[planId]`
可以保留为兼容或诊断入口，但不应成为正常操作的必经路径。

选择共享工作台的条件：

- 列表仍是操作者的主要上下文；
- 编辑是短周期、结构化、可一次保存的动作；
- 不需要在多个子资源间导航；
- 关闭后必须回到原列表位置和筛选状态。

### 3.3 参数网格按比较密度响应

数字字段不需要占满半屏。已接受的布局原则是：

- 默认单列；
- `sm` 两列；
- `xl` 三列；
- 数值输入和单位使用独立 grid cell；
- 单位不得用 absolute 定位覆盖输入值；
- 输入和单位共享 `--admin-compact-control-height`；
- 说明紧随字段，但不挤进输入框。

四列在超宽桌面上看似更密集，却会放大中文标签、单位和帮助文案的碰撞风险。
三列是当前字段长度和 1280/1600 PC 工作面的更稳妥上限。

### 3.4 可见文案短，完整语义不能丢

“还原当前已保存值”和“恢复 Free 建议值”在工具栏中过长。可见文本可以缩短为
“还原”和“默认”，但 `aria-label` 或 `title` 必须保留对象和结果：

- 还原：丢弃当前未保存编辑，恢复最近已保存值；
- 默认：载入当前套餐建议值，但不自动保存；
- 保存：唯一主操作。

短文案是密度优化，不是语义删减。

### 3.5 隐藏 UI 与删除能力是两件事

发布历史表和高级 JSON 覆盖项已从正常工作台移除，原因是它们让常规维护
变成低频工程控制台。但是当前仓库的删除清单已明确：

- Admin 列表/详情投影不再返回完整 `versions`；
- 结构化 PATCH 拒绝未知原始覆盖对象；
- 未暴露但仍受支持的商业字段在更新时必须保留；
- `PlanVersion`、版本发布和 JSON 持久化仍服务于套餐初始化、活跃订阅、
  结账、权益快照、运行预算和审计证据。

因此，后续删除必须从依赖图和可执行证明出发，不能从“界面看不到”反推
“后端已无价值”。

## 4. 从服务状态得到的产品经验

### 4.1 队列优先，不默认使用左右检查器

右侧检查器只有在操作者需要连续选择多行并保持同屏比较时才有价值。本页最终
发现检查器重复了表格和客户详情，且占用横向空间，因此应合并回全宽表格。

保留检查器至少要同时满足：

1. 切换对象不应离开当前任务；
2. 右侧信息显著多于表格但又不值得进入详情页；
3. 操作者确实需要在多行间高频来回比较；
4. 检查器提供独有动作，而不是重复入口。

不满足这些条件时，优先使用语义表格加明确详情链接。

### 4.2 可读身份优先，内部 ID 默认隐藏

操作者首先识别的是客户名称或邮箱，不是 `acct_*` 标识。身份展示顺序应为：

1. 已知邮箱；
2. 可读客户名称；
3. “未命名客户”；
4. 内部 ID 只在技术信息或详情诊断中出现。

邮箱使用原生账户详情 `<a>`。点击或键盘激活链接只导航，不触发行选择逻辑；
表格的其他区域也不应伪装成第二个详情链接。

### 4.3 正常状态不需要“问题”说明

“套餐、订阅、站点、密钥和账单证据已对齐”对正常行没有下一步意义。正常行
只需要安静状态和关键容量事实；警告或错误行才需要问题原因、影响和动作。

这条规则可以推广为：

> 正常信息用于确认，异常信息用于决策；不要让确认文案占用决策列。

### 4.4 状态筛选默认“全部”

如果页面没有收到显式 `status` 参数，默认值是 `all`，而不是偷偷使用
`needs_action`。原因是：

- 默认结果与选择器文案一致；
- URL 可准确重建页面；
- “清除筛选”可以通过删除参数恢复默认；
- 操作者不会因为隐式过滤误判客户总量。

显式的 `needs_action | ok | warning | error | inactive` 继续由 URL 拥有。
排序和其他可分享筛选遵守同一规则；临时焦点不是业务状态，不应长期进入 URL。

### 4.5 动作必须跟随原因

- 正常：无处理按钮；
- 警告/错误：在该行显示一个与原因对应的上下文主动作；
- 客户详情：保持普通导航链接，不与异常处理动作争夺主次；
- 技术信息：进入详情/诊断，不在队列堆叠。

“每行都放一个按钮”不是一致性，而是把无意义选择强加给操作者。

## 5. 可复用的 Admin 操作台规范

### 5.1 开工前必须声明

每个页面变更先写清：

| 项目 | 必答问题 |
| --- | --- |
| Page model | 是 `queue`、`detail`、`configuration` 还是其他已登记模型？ |
| Operator job | 操作者要找到什么、判断什么、做什么？ |
| Primary action | 正常路径唯一主操作是什么？ |
| Secondary action | 哪些动作不会提交或不会改变远端真值？ |
| Destructive action | 是否存在删除、清空、停用或不可逆影响？ |
| State ownership | URL、远端数据、表单草稿、临时 UI 分别由谁拥有？ |
| Low-frequency disclosure | ID、原始证据、调试字段和高级参数去哪里？ |
| PC gate | 900、1280、1600 下分别如何验证扫描和操作？ |

### 5.2 信息放置规则

| 信息 | 默认位置 |
| --- | --- |
| 识别对象和横向比较所需事实 | 队列表格 |
| 当前对象的短周期结构化编辑 | 共享 workbench dialog |
| 长文本、多个子资源、诊断证据 | 独立详情页或诊断页 |
| 内部 ID、原始 JSON、历史记录 | 低频 disclosure 或诊断 |
| 正常状态说明 | 通常省略 |
| 警告/错误原因和影响 | 当前行 |
| 恢复动作 | 紧邻失败状态 |

### 5.3 判断内容是否多余

对每项内容依次提问：

1. 它能改变操作者当前判断吗？
2. 它能直接支持下一步动作吗？
3. 它是否已经在同屏或详情重复？
4. 它是否属于工程诊断而非日常运营？
5. 删除后是否仍可从明确入口找到？

前两项都是否、后三项任一为是时，默认移除或降级。

### 5.4 判断动作是否重复

同一对象应只有一个明显的正常入口。以下组合通常是重复：

- 可点击整行 + 可点击名称 + “详情”按钮；
- 列表“检查” + 右侧“详情” + 独立详情页；
- “查看限制” + “修改套餐”，但两者最终打开同一个维护上下文；
- “打开客户”同时出现在行和检查器。

只有当入口指向不同操作者任务且标签能准确区分时才同时保留。

## 6. 工程交付规范

### 6.1 一个批次只解决一个操作者问题

每批必须锁定：

- 一个路由或一个共享 seam；
- exact files；
- 明确 non-goals；
- 不改变的 API、后端、数据库、i18n 和其他路由；
- 回滚方式；
- 最窄有效门禁。

套餐、服务状态、M4 基础设施和生产发布必须分批。发现相邻问题时记录 backlog，
不顺手扩进当前 PR。

### 6.2 保留“三个唯一”

并行工作时始终保持：

1. 一个冲突文件域只有一个负责会话；
2. 同一时刻只有一个 Cloud 人工 merge lane；
3. shared M4 candidate 只有一个明确 owner。

每次接管前重新读取当前状态和 owner。较早的“已释放”回执可能已被后续任务
取代，不能当作永久许可。

### 6.3 证据分层

| 证据层 | 可证明 | 不可证明 |
| --- | --- | --- |
| 本地 focused/static | 当前 seam 结构和行为通过 | M4 运行、合并或生产 |
| 本地受控 PC browser | 指定 revision 的布局和交互 | M4 transport 或线上可见 |
| M4 candidate | 候选在集成运行时工作 | 已进 `master` |
| PR required checks | 推送 revision 满足合并门禁 | 已合并、已上 M4 |
| merged master | 代码成为集成真值 | M4 正在运行它 |
| M4 accepted | 干净当前 master 已 promotion 并通过相关 smoke | 生产或真实客户接受 |
| production validated | 经单独授权的生产流程完成 | 产品价值或 GA |

浏览器传输慢、无 Admin 会话或端口被既有进程占用时，证据记为
`not_counted`，不得猜凭据、杀他人进程或把登录页当成产品通过。本地受控
Playwright 可以证明产品行为，但必须如实标明不是 M4 登录后证据。

### 6.4 M4 必须 fail closed

- 普通 Cloud 源码优先 `m4:preview:sync`；
- 构建指纹变化时让 sync 拒绝，再按规范选择 deploy；
- 端口、slot、container 或 volume 有明确 owner 时不覆盖；
- expired/drifted slot 使用仓库受控 status/release/recovery 路径；
- 不用手工 Docker 清理掩盖治理问题；
- 产品修复和基础设施 guard 分成独立批次；
- PR 合并后从干净当前 master promotion，才可称为 accepted。

### 6.5 测试是产品契约

交互改变时，既有 E2E 断言可能成为旧产品契约。应更新为新行为，而不是简单
删除连通性证明。例如：

- 退役检查器时，测试应验证全宽表格和详情链接；
- 邮箱成为链接时，测试应验证链接导航与行交互不串扰；
- 默认筛选改为全部时，测试应验证 URL 无参数、清除参数和显式状态；
- 数字网格改变列数时，测试应验证 900/1280/1600 几何和单位不重叠。

与当前批次无关的跨路由基线失败单独记录，不借机扩 scope。

## 7. 常见反模式

| 反模式 | 后果 | 正确替代 |
| --- | --- | --- |
| 默认采用左右布局 | 列表变窄，详情重复，未来字段继续挤压 | 先证明同屏检查器有独有价值，否则全宽表格 |
| 所有事实都放卡片 | 横向比较困难，首屏密度低 | 重复字段使用语义表格 |
| 每行都有操作按钮 | 正常行产生无意义选择 | 仅异常行显示上下文动作 |
| 用内部 ID 作为主身份 | 人无法快速识别对象 | 名称/邮箱优先，ID 低频披露 |
| UI 隐藏后立即删后端 | 破坏审计、结账或运行时依赖 | 先依赖审计和可执行删除证明 |
| 用 absolute 放单位 | 多语言和窄宽度下重叠 | 数值与单位独立 grid cells |
| 本地通过就说“已上线” | 用户在目标 URL 看不到变化 | 报告 exact revision 和最高证据层 |
| 旧 owner 回执当作当前锁 | 覆盖并行候选或 M4 现场 | 每次接管前重新 status |
| 浏览器不通就无限重试 | 长时间占用 shared M4 | 分级为 not_counted，保留现场并释放 |
| 为修一个页面顺手修全站 | scope、回滚和 CI 责任失控 | exact files，一批一 PR |

## 8. Definition of Done

### 8.1 产品与界面

- [ ] 页面模型和 operator job 已声明；
- [ ] 首屏能完成“找对象、判状态、进动作”；
- [ ] 同一正常任务只有一个明显入口；
- [ ] 正常状态安静，异常才提升原因、影响和动作；
- [ ] 客户名称/邮箱可读，内部 ID 默认隐藏；
- [ ] URL 筛选默认值、显式值和清除行为一致；
- [ ] 低频技术证据有明确去处；
- [ ] 900 可换行但不截断，1280/1600 保持主要工作面；
- [ ] 焦点、键盘、链接和行交互不串扰；
- [ ] 没有新增第二商业真值或 WordPress 控制面。

### 8.2 工程与交付

- [ ] 从最新 `origin/master` 的干净、锁定工作树开始；
- [ ] exact files、non-goals 和 rollback 已记录；
- [ ] contract、type、target lint、`check:admin-ui` 按风险通过；
- [ ] 物质布局变化通过 `check:admin-ui:visual` 和多视口 PC gate；
- [ ] shared behavior 变化时更新相关跨路由契约；
- [ ] M4 命令与 changed fingerprint 匹配；
- [ ] M4 owner、Cloud merge lane 和浏览器证据状态如实记录；
- [ ] 只精确暂存任务文件；
- [ ] PR required checks 通过；
- [ ] 合并后从干净当前 master 完成 promotion、status 和相关 smoke；
- [ ] 明确区分 merged、M4 accepted、production 与 human acceptance。

## 9. 后续事项

### 9.1 可直接复用

- 把本文件的内容判定、动作判定和 DoD 用于其他 Admin queue；
- 优先消除重复检查器、重复详情入口和正常行无意义动作；
- 新的紧凑表单继续复用共享 `--admin-*` token 和 Admin primitives；
- 每次发布继续使用 exact-file PR 和分层证据。

### 9.2 需要独立授权和依赖审计

- 是否最终删除通用套餐版本发布、`PlanVersion` 和 JSON persistence；
- 是否进一步移除 `/admin/plans/[planId]` 兼容/诊断路由；
- 是否把服务状态中的其他技术字段迁移到统一客户诊断页；
- 是否增加 M4 deploy 对过期 frontend slot 占用共享 volume 的预检 guard。

这些事项不能混入下一次视觉微调。每项都必须有独立 change envelope、
依赖图、迁移/回滚计划和可执行证明。

## 10. 收口原则

本阶段最值得保留的不是某一张截图，而是三条方法：

1. **从操作者任务删内容**：不是从后端字段列表加内容；
2. **从依赖证据删能力**：不是从界面不可见推断能力无用；
3. **从证据层报告完成**：不是把本地通过、M4 candidate、合并和生产混成
   一个“已完成”。

后续页面如果重新出现卡片堆叠、重复入口、内部 ID 主导、无意义正常动作或
模糊的部署状态，应优先回到这三条原则，而不是继续做局部像素修补。
