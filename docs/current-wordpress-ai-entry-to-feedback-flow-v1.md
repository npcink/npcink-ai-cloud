### 有界只读诊断补充（2026-09-08）

- 实际安装版本：官方 `ai/ai.php` 为 1.3.0，Addon 为 0.2.0。
- 已确认日志桥兼容性缺陷：安装目录下
  `npcink-cloud-addon/includes/class-cloud-wordpress-ai-connector.php:1037`
  的文本任务传入 `type=text`，日志桥直接转交该值；官方
  `ai/includes/Logging/AI_Request_Log_Manager.php:162` 仅接受
  `ai_client`、`mcp_tool`、`ability`，遇到 `text` 返回 false。
  Addon 未处理该返回值。视觉任务还传入 `vision`，同样不在允许集合。
- 使用实际安装的官方 PHP 类，在不加载 WordPress、不连接数据库、不调用模型的
  隔离进程中复现：`Unsupported log type: text. Supported types are:
  ai_client, mcp_tool, ability.`，返回 false。这证明日志桥不能以当前类型写入，
  但不证明此次请求的所有其他日志前置条件已满足，也不代表 Cloud 运行记录丢失。
- 官方 `Logging_Integration.php` 包装的是 AI Client SDK HTTP transporter；
  不能仅凭安装了官方日志功能，就假定 Addon 的独立 Cloud 调用自动被记录。
- 新开 Cloud Portal 页面实际重定向至登录页，故本轮未取得该请求的运行详情。
  实际模型、Provider 和站点背景应用状态仍未核实，不以设置开关代替运行证据。
- Addon 的 `class-cloud-editor-assist-quality.php` 在生成时记录文章 ID 与结果哈希，
  在 `wp_after_insert_post` 按同一文章 ID 匹配保存结果；精确匹配记为
  `saved_exact_output`，未匹配仅记为 `saved_after_generation_unmatched`。
  后者不能直接解释为“修改后采用”。复制旧建议至另一测试草稿，不能证明原请求
  的采用关联，因此未创建草稿、伪造关联记录或改动原文章。

本轮仅补充诊断文档，未修复插件、变更设置、执行新模型请求或发布文章。

没有投影这些 generation-context metadata。因此本次运行同时存在“向量调用发生”
和“公开结果无法证明注入”的事实，不能把前者升级为后者。补齐只读证据投影是
下一项最小 Cloud 改动，仍不涉及 WordPress 写入或模型路由。

## 结论

这条流程是当前产品架构的正确描述，且 Cloud 侧的关键所有权边界已经落地：Cloud 执行并返回建议、上下文和运行证据，WordPress 负责审阅和最终写入。
