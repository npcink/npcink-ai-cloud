## 1. 原始目标

Cloud Admin 是内部操作台，主要用于数据查看、配置、诊断和有限的
Cloud-owned 操作。它不是面向普通用户的消费产品界面。

本阶段确认的目标是：

1. 简单：减少无业务价值的装饰、卡片、嵌套边框和重复说明；
2. 直观：让对象、状态、异常原因和下一步操作可以一次扫读；
3. 高效：优先支持 PC 端高频操作，允许使用表格和紧凑工作台；
4. 稳定：不同开发者和 AI 后续修改时，不能重新退回各页面自由发挥；
5. 有边界：Cloud Admin 只管理 Cloud-owned 服务面事实，不成为第二个
   WordPress 控制面、能力注册表、工作流注册表或最终写入权威。

Cloudflare Access、边缘网络和开发预览链路可能让部分页面打开较慢。
网络等待和信息架构是两个问题：本阶段不以加载速度代替界面审查，也不因
预览链路慢而接受低效布局。

## 3. 从参考产品中学到了什么

`ref.tools` 的设置页提供了有用的参考，但借鉴的是任务结构，不是视觉复制：

- 左侧分类稳定存在，右侧只显示一个当前设置域；
- 当前选中项使用安静背景，不依赖大色块；
- 标题、输入和值之间层级清楚；
- 分组靠对齐、间距和细线建立，而不是每组一个重卡片；
- 低频信息不与主要配置竞争首屏空间。

没有照搬的部分包括等宽字体、品牌化装饰、面向消费产品的展示卡片和与
Cloud Admin 工作无关的交互。参考产品只帮助验证方向，实际设计仍由
Cloud 的操作任务、字段结构、风险和边界决定。

## 4. 核心设计思路

### 4.1 先确定操作任务，再确定视觉形式

每个页面先回答：

1. 操作者要判断什么状态？
2. 当前最需要处理什么？
3. 正确操作入口在哪里？

只有在这三个问题明确后，才选择表格、配置工作台、详情页或诊断面板。
“看起来统一”不能优先于任务差异。

### 4.2 按信息结构选择表格

表格不是默认装饰，而是比较工具：

- 多个对象重复相同字段时，使用语义数据表；
- 简单设置重复“设置项 / 当前值 / 操作或说明”时，使用三列配置表；
- 多个设置组字段结构不同但每次只编辑一个时，使用“稳定目录 + 活动面板”；
- 邮件、支付等异构字段不强行伪装成数据表，保持扁平表单；
- 原始证据、调试参数、删除和恢复操作放入低频入口。

判断标准不是“能不能画成表格”，而是“表格能否提高横向比较和纵向扫描”。

### 4.3 密度是一个系统，不是缩小高度

紧凑模式必须同时处理：

- 控件高度；
- 垂直和水平内边距；
- 字体行高；
- 标签与控件比例；
- 圆角；
- 焦点轮廓；
- 表头和数据行节奏；
- 工作台最大宽度。

早期只压缩高度时出现了文字显示不全。修正后，compact density 统一采用
约 `32px` 控件、约 `40px` 行、`4px` 圆角和更安静的焦点处理。默认密度
保持不变，避免一个试点无意改写全部 Admin 页面。

### 4.4 一次只保留一个主要结构边界

表格已经有表头和行分隔时，不再叠加强外框、重圆角、分组卡片和同等强度
的内部线条。交互控件保留必要边界，普通内容主要依靠对齐和低对比分隔。

“移除边框”不是把所有线删掉，而是只保留解释结构或表达交互性的线。

### 4.5 操作按频率和风险分层

- 高频主操作直接出现，例如配置、保存；
- 高频次操作保持相邻，例如测试、同步；
- 低频维护操作在稳定的行内区域或 disclosure 中；
- 删除、清空、停用和恢复不进入默认保存区；
- 危险操作必须说明影响对象并单独确认；
- 失败恢复入口靠近失败状态，不占用正常工具栏。

这解决了“更多操作”展开后位置奇怪、遮挡数据和操作链路过长的问题。

### 4.6 正常状态保持安静

正常、就绪、已配置不需要强烈装饰。警告、待确认、失败、停用和破坏性状态
才获得更高视觉权重。状态始终包含文字，不能只依赖颜色。

## 5. 风格一致性如何变成工程约束

单独写一份设计说明不足以阻止后续漂移。本阶段把规则投射到五层：

| 层 | 约束 |
| --- | --- |
| 信息架构 | `cloud-admin-information-architecture-v2.md` 定义六种页面模型 |
| 实现标准 | `cloud-admin-ui-standard-v1.md` 定义密度、层级、表格、弹窗和凭据规则 |
| 路由清单 | `frontend/admin-ui-manifest.json` 记录 26 个路由及允许的迁移债务 |
| 共享实现 | `AdminDataTableFrame`、`AdminConfigurationTable`、`AdminWorkbenchDialog`、`AdminCredentialField`、`AdminSettingsWorkbench` 等 |
| 自动验证 | `check:admin-ui`、全量 frontend contracts、Playwright PC 截图和 PR 模板 |

后续 AI 不应通过“参考截图后重新写一套 CSS”保持一致，而应：

1. 声明页面模型和操作者任务；
2. 复用共享组件和 `--admin-*` 几何 token；
3. 将新规则写入结构契约；
4. 用确定性 fixture 和截图验证关键工作面；
5. 在 PR 中说明主操作、次操作、危险操作和低频信息去向。

### 做得好的地方

- 主工作区存在未提交内容时始终使用独立工作树，没有 reset、stash 或混合暂存；
- 用户每次截图反馈都被转化为可执行规则，而不是只做一次性像素调整；
- 没有为了视觉统一改变 API、凭据生命周期或 Cloud/WordPress 所有权；
- 将“表格优先”落实为多种语义组件，而不是一张万能表；
- 视觉测试同时验证截图和关键几何，避免只看像素差；
- 明确区分 local verified、M4 candidate、PR verified、merged 和 M4 accepted；
- 合并后从干净 `master` promotion，避免候选代码成为最终运行真相。

### 下次重点关注

1. 发布前先确认用户将在哪个 URL 验收，并在每次更新中报告 evidence state；
2. 共享弹窗、凭据、导航或焦点行为变化时，发布前运行完整 frontend contracts；
3. compact 设计先验证最长中文标签、最长模型名和最窄目标 PC 宽度；
4. 一个页面只建立一个主工作面，不用多个卡片同时争夺注意力；
5. 只有真实操作阻力明确时才迁移下一页，不开展无目标的全站视觉翻新。

### 2026-07-28 补充审视

后续讨论进一步明确：平台管理员设置页仍应向高效表格方向演进，但不能把
“表格优先”误解为“所有内容必须放进表格”。当前最需要防止的两种偏差是：

1. **过度表格化**：长文本编辑、异构设置组和危险操作被压进同一张表，
   反而降低可读性并模糊风险；
2. **资源分散**：为了视觉统一同时改造多个低频页面，与 README 中优先证明
   核心 AI 用户链路的主攻方向冲突。

改进方式是把后续路线准备好，但只在得到明确授权或出现真实操作阻力时，
一次迁移一个页面。页面必须先声明对象、操作者判断、主操作和风险，再选择
数据表、配置表、目录工作台或扁平编辑器。

## 7. 推荐开发流程

### 7.1 调查

1. 读取真实页面、当前 DOM、截图和操作路径；
2. 区分加载慢、数据为空、权限阻塞和布局问题；
3. 声明页面模型、操作者任务和 Cloud 边界；
4. 列出主操作、次操作、危险操作和低频信息；
5. 选择一个参考页面，不同时模仿多个视觉体系。

### 7.2 设计

1. 先写文字版信息顺序；
2. 再决定表格、配置表、目录工作台或扁平表单；
3. 为 PC 工具栏和表格列分配宽度；
4. 把正常状态降噪，把异常和下一步提升；
5. 明确哪些解释需要常驻，哪些放入 tooltip、disclosure 或文档。

### 7.3 实现

1. 从当前 `origin/master` 建立干净 `codex/*` 工作树；
2. 优先扩展共享 primitive 的显式模式，不在路由中散落魔法尺寸；
3. 保留原有 API、错误、dirty-state、凭据和确认行为；
4. 为结构规则添加 contract，为关键工作面添加确定性 PC 截图；
5. 精确暂存当前模块文件。

### 7.4 验证和交付

```text
focused contract/type/lint
  -> check:admin-ui
  -> full frontend contracts when shared behavior changed
  -> check:admin-ui:visual
  -> M4 candidate for application source
  -> PR required checks
  -> merge into master
  -> clean master M4 promotion
  -> human visual acceptance
```

不能用 `200` 代替视觉验收，也不能用截图通过代替保存、测试、焦点返回、
凭据替换和未保存离开保护。

## 8. 后续策略

README 当前要求暂停宽泛的 Admin 治理页面和大范围控制台扩张，优先证明
核心 AI 用户链路。因此下一阶段不应继续为了“统一”批量翻新所有页面。

合理的后续方式是：

1. 保持现有四个参考页面作为可执行范例；
2. 只有在真实操作中发现明确阻力时，一次迁移一个页面；
3. 优先清理 manifest 中现存的 route-local dialog 和 credential migration
   debt，不增加新的例外；
4. 新页面默认使用标准密度；只有高频 PC 配置任务经过审查后才启用 compact；
5. 把主要开发资源重新集中到核心 AI 路径，Admin UI 只做阻塞性修复和必要
   的运行配置支持。

## 9. 平台管理员设置页的表格化路线

### 9.1 已确认方向

设置页继续采用 PC-first、简单、直观、高效的工作台方向。表格承担重复字段
的比较和扫描，目录承担异构设置组的切换，扁平编辑器承担长文本或复杂内容。
不建立一张跨领域的“平台所有设置”巨型表，也不为了共用视觉组件合并 API、
保存事务、权限、审计或数据所有权。

页面形式按信息结构选择：

| 信息结构 | 首选工作面 | 适用条件 |
| --- | --- | --- |
| 多个对象重复相同字段 | 语义数据表 | 需要横向比较状态、数值和下一步操作 |
| 一个固定设置组，字段短且稳定 | 三列配置表 | 重复“设置项 / 当前值 / 操作或说明” |
| 多个设置组结构不同 | 设置目录 + 单一活动面板 | 操作者每次只处理一个设置域 |
| 长文本、模板或复杂内容 | 扁平编辑器 | 表格不能提高比较或扫描效率 |
| 原始标识、调试参数、危险维护 | disclosure 或上下文入口 | 低频、恢复性或高风险操作 |

### 9.2 当前基线：向量设置已完成

PR `#317` 已将 `/admin/vector-settings` 整理为本路线的固定配置参考页：

1. 首部只保留紧凑状态摘要；
2. 固定档案、SiliconFlow 凭据、Zilliz Endpoint、Token 和 Collection
   进入连续三列配置表；
3. 连接、索引和真实检索证据进入独立验证结果表；
4. 技术标识和索引策略默认收起；
5. 凭据统一使用 `AdminCredentialField`，存量密钥不回显；
6. 配置只有一个“保存配置”主操作，重建只在索引状态需要处理时出现。

因此 `frontend/admin-ui-manifest.json` 中
`legacyRouteLocalCredentials` 已清空。后续不得重新增加 route-local
密码框作为捷径。

### 9.3 后续页面优先级

| 优先级 | 页面 | 推荐结构 | 为什么 |

| P1 | `/admin/credit-packs` | 积分包目录表 + 共享编辑工作台 | 对象字段重复且需要比较，当前最适合直接获得表格效率 |

| AI 积分 | 可分配额度 |
| 价格 | 金额和币种 |
| 有效期 | 固定期限或长期有效 |
| 推荐层级 | 适用套餐或客户层级 |
| 门户可见 | 是否允许客户门户展示 |
| 状态 | 启用、停用或待处理 |
| 操作 | 一个明确的“配置”入口 |

目录负责比较和选择，创建或编辑进入共享工作台。保存是唯一主操作；停用、
删除和其他危险操作不与默认保存共用 footer。长名称、金额、层级和状态必须
在 PC 目标宽度下完整可辨，不依赖 hover 才能理解主要事实。

### 9.5 实施和验收约束

每个设置页改造前必须记录：

- 页面模型、操作者任务和 Cloud 所有权边界；
- 主操作、次操作、危险操作及低频信息去向；
- 表格列宽预算和最长中文、域名、模型名或集合名 fixture；
- loading、empty、filtered-empty、error、ready、dirty 和 disabled 状态；
- 共享 primitive、参考页面和必要的浏览器证据。

PC 验收以目标工作面为准：

1. `1440px` 视口下，前两个屏幕高度内能完成主要判断和操作；
2. compact 模式约使用 `32px` 控件、约 `40px` 表格行和 `4px` 圆角，
   但不得裁切文字或焦点轮廓；
3. 页面只保留一个主要结构边界，控件保留必要交互边界；
4. 搜索、筛选和表格保持稳定，不因反馈、弹层或低频操作发生位移；
5. 凭据只显示“已保存/保持不变”，替换必须显式触发且取消后清空草稿；
6. 离开前保护 dirty state，错误靠近对应字段或操作，成功反馈不遮挡数据；
7. 共享行为变化时同时运行聚焦 Admin gate、完整 frontend contracts 和
   PC 视觉证据；应用源码在合并前后分别保留 M4 candidate 与 accepted
   evidence。

本路线不批准全站批量翻新、API 或数据所有权合并、生产部署、凭据回显，
也不把 M4 `200`、CI 绿色或截图单独当成人工可用性验收。
