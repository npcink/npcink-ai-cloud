# 阶段 1：免费试用商业验证计划（2026-10-06）

Status: operator-confirmed plan; development candidate preparation. 尚未启动试用；
T+0、招募名单、运行预算配置及真实链路验收待操作者提供。本文不构成 PR、
合并、生产发布或真实付费调用授权。

## 1. 目标与确认口径

用四周、3–5 位实际写文章的站长验证使用价值、留存和成本，为是否进入邀请
收费阶段提供证据。免费试用不能证明购买意愿，购买意愿留到下一阶段验证。

本次确认覆盖最初的“标题/摘要竖切、每周 50 次、手工开户”起点：

| 项目 | 本次确认 |
| --- | --- |
| 招募 | 定向介绍站点，正常自注册；不做邀请码、白名单或邀请管理 |
| 开户 | 邮箱验证注册或 QQ 首次登录；验证成功即获得账户级 Free |
| 额度 | 复用现有 Free，不新增试用套餐、周限额或周重置 |
| 代码基线 | 300 AI credits / 30 天周期，1 个站点；以实际账户权益显示为准 |
| 使用范围 | 当前官方 WordPress AI 插件经现有连接实际支持的能力，按写作需要自然使用 |
| 图像 | 保留可用文生图、ALT；参考图编辑暂缓，不在本轮更换模型或修改协议 |
| 支付 | 免费试用不付款、不充值、不自动转收费；不修改支付域配置 |
| 投入 | 不新增报表系统、埋点平台、试用管理后台，不为制造数据发起付费调用 |

Cloud 只拥有账户权益、运行与用量证据；WordPress 保留建议审阅、采纳、保存
和发布的最终真相。平台账单是成本侧真相，Cloud run 和 agent_feedback 是
行为侧证据，两者不能互相替代。

## 2. 三个假设与统计规则

| 假设 | 不变的判据 | 计算 |
| --- | --- | --- |
| H1 使用价值 | 采纳率 ≥40% | 可关联、去重的采纳事件 / 建议展示 |
| H2 持续使用 | 两周留存 ≥50% | 首周活跃种子中第二周仍真实使用人数 / 首周活跃种子人数 |
| H3 成本可承受 | 单活跃用户月成本 ≤¥5–7 | 对应拟议 ¥50–70/月价格的 10%，不改变现有售卖价格 |

H1 保留原生 agent_feedback 的 accepted、edited_before_accept 采纳证据，
按建议标识关联展示并去重。现有 summary 的 accepted_rate 是采纳反馈占
全部反馈，不能直接填入“采纳 / 展示”。编辑辅助 presented 事件、精确保存
匹配和人工记录分列来源；不得把生成完成、未匹配保存或人工确认冒充原生
采纳事件。无法确认展示或反馈覆盖时记录“证据不足”，不将缺失当拒绝。
需要启用的已有观测同意设置按现行规则处理，不为试用扩大采集。

H2 的真实使用是站长在正常写作中成功使用 AI 结果；仅登录、健康检查、
开发调用不算活跃。纯失败尝试单列为使用阻碍。固定首周种子队列；晚加入者
和其他自行注册者单列，不改动首周分母。首周无人活跃时 H2 不可计算。

H3 用第三方平台实际消费而非充值金额。优先按模型、输入/输出 token、
图片等实际计费单位归因；无法直接归因时，用各用户价格加权用量占比分摊
同类消费。仅有次数时采用次数比例并注明较粗估算。平台合计、试用分摊、
开发/自测与无法归属消费分别列示，不把未归属金额计为零。

- 周月成本估算 = 本周试用消费 / 本周活跃人数 × 30/7。
- 四周月成本估算 = 四周试用消费 / 四周活跃用户周数之和 × 30/7。
- 同时报告实际消费；零活跃时标记不可计算。
- ≤¥5 满足两个拟议价格档；¥5–7 仅满足较高价格档；>¥7 超出目标。
- 包含第三方实际计费的失败及重试，不能仅计算成功请求。

## 3. 种子、周期与周报

观察样本为 3–5 位会真实写文章的熟人站长，名单待提供。仓库中使用 S1–S5
等匿名标识；账户/站点映射由操作者受控保存，不提交邮箱、凭据或文章正文。
样本数量是观察队列大小，不是注册入口限制。

T+0 待操作者指定，功能在实际试用环境可用且前置条件完成后开始；计划日期
不是开始日期。时间统一 Asia/Shanghai，每周为固定半开区间：
第 N 周 [T+0 + 7(N−1) 天, T+0 + 7N 天)。查询转换为 UTC 后执行。

每周由操作者带回同一时间段的第三方消费明细，核对：

1. 各用户所属站点的 distinct run_id、能力使用、成功、失败和错误分类。
2. Provider 调用的模型、token、图片计费单位与平台消费；避免与 run 汇总重复累加。
3. 可关联展示与采纳、证据覆盖、人工补充和一个主要使用阻碍。
4. H1/H2/H3 的分子、分母、估算方法与判据比较；H2 在第二周正式核对，
   后续周相对首周的持续使用另列，不能冒充“两周留存”。

追加 docs/history/trials/<年>/trial-weekly-report-<第N周>-<日期>.md。
报告只记事实与估算，不提前下商业结论。没有明细或观测不完整时记缺口，
不生成虚构周报、不安排定时任务、不要求用户逐项测试所有能力。

## 4. 前置四件事与开始门槛

| 前置事项 | 当前状态 | 开始前证据 |
| --- | --- | --- |
| Provider 预算硬上限 | 实现已有；目标环境是否启用、数值及覆盖尚未核实 | 已启用且实际付费 Provider 的日/月限额已配置，配置摘要由操作者确认 |
| 免费账号开户 | 正常自注册已确认；注册即 Free 的改动待候选验证及正式交付 | 邮箱和 QQ 路径、旧账户补齐、无站点额度可见，发布/环境状态分列 |
| 链路六条 Done | 操作者自测状态待提供 | 对照现有 checklist，复用有效证据，缺项在正常使用中补齐 |
| 一句式告知与页脚 ICP | 完成状态待操作者核对 | 告知与实际支持范围一致，页脚 ICP 信息核对完成 |

建议告知：“当前为免费试用，额度按 Free 套餐执行；AI 结果请核对后使用，
参考图编辑暂不可用。”

另需观察名单就绪并指定 T+0。退款、网信登记、公司设立等保持原先后移安排；
本文不对法定义务作豁免结论。支付已有代码或历史实测不等于本次启用支付。
P6 预算是事前拦截，第三方账单是事后核对，Free credits 是用户权益，
三者分别保留。预算关闭或缺少覆盖不得据此宣称已具备成本保护。

## 5. 开发、交付和 T+4 报告

阶段 1 文档与机制盘点按 docs-only 门禁独立本地提交。阶段 2 只调整 Free
激活时机、旧正常账户登录补齐及相应 Portal 说明、测试和 ADR；无迁移，
保留 Addon 站点验证及历史无订阅兜底。具体机制见配套盘点。

每阶段独立验收；同一阶段连续两次失败即停并报告。开发付费调用预算为 0；
development lane 的候选验证不授权 PR 或生产。PR 发布前仍需操作者确认，
生产操作另行授权；不要把 M4 candidate 当作 merged、accepted 或生产。

第四周追加 docs/trial-stage-commercial-validation-report-<日期>.md：

- 四周事实汇总及第三方消费对账、分摊与不确定性；
- 三假设逐条“达到 / 未达到 / 无法判断”，不得以小样本证明大规模成立；
- go/no-go 建议与理由：证据完整且三项达到可建议进入下一阶段；
  有未达到项则列主要阻碍与最小修正；关键证据缺失时建议延长或补证据；
- 进入阶段 2 前置清单：操作者决定收费范围/价格、另行核对收费阶段合规及
  支付/退款就绪度、重新确认预算和环境、正常付费路径与退出处理；
- 在本计划顶部追加报告状态指引，保留原确认和历史证据。
