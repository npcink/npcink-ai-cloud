## 1. Executive conclusion

The work began with a plausible observation: service problems are ultimately
handled for a specific customer, so Service status might belong inside
Customers.

That observation was correct about the action destination but not about the
queue's information architecture.

- Customers answers: who is this customer and where is the complete record?
- Service status answers: which customers may have a problem, why, and what is
  the next action?

The final design keeps the two routes separate and connects them through
contextual deep links. `/admin/accounts` is the stable customer directory.
`/admin/coverage` is the cross-customer problem queue. Customer-specific
actions live in task tabs on `/admin/accounts/{accountId}`.

The key reusable principle is:

> The place that discovers a problem and the place that owns its resolution
> may be different. Connect them; do not merge them merely because they share
> an object.

## 2. Decision history

### 2.1 Initial consolidation hypothesis

The first hypothesis grouped customer information and service problems under
one Customers workspace with needs-action and all-customer views. It had one
advantage: every problem could lead to a customer.

The weakness was that “all customers” and “needs action” require different
defaults, sorting, columns, reasons, and completion conditions. One route would
have recreated two products as internal tabs and made the customer register
unstable whenever problem rules changed.

The hypothesis was rejected before historical compatibility existed. This was
the right time to remove the ambiguity rather than add a permanent switch.

### 2.2 Stable route boundary

PR #428 implemented ADR-037:

- Customers became a name-ordered semantic directory;
- Service status became the needs-action problem queue;
- risk reasons, row inspector, identity audit, and destructive access actions
  left the customer list;
- problem rows link to the detail surface that owns the action;
- customer detail gained a dedicated Access task tab.

### 2.3 Customer creation and direct actions

PR #430 tightened the high-frequency flow:

- Add customer remains in the directory but opens the shared Admin dialog;
- Account ID is generated by the Cloud commercial domain;
- a successful create opens the generated customer detail;
- the header no longer duplicates package management;
- a `More` menu containing only one action was removed;
- the direct Account state action stays with Overview.

This reinforced two rules:

1. preserve list context for bounded create/edit work;
2. do not add disclosure merely to hide the only available action.

### 2.4 Detail tabs and information density

Customer detail settled on six task tabs:

- Overview;
- Commercial;
- Credits and usage;
- Sites;
- Access;
- Audit.

Commercial and Credits initially used large side-by-side cards. The layout
looked orderly but produced low information density, uneven empty space, and
weak row-by-row comparison.

PR #431 replaced that composition with:

- compact current-coverage summary;
- semantic package comparison table;
- semantic top-up comparison table;
- semantic resource-limit table;
- AI credit adjustment behind a low-frequency disclosure;
- shared `AdminDataTableFrame`;
- package-specific accessible action names.

The final rule is not “everything becomes a table.” Tables are used only for
repeated comparison. A single conclusion, form, or explanation remains a
summary, form, or disclosure.

## 3. Delivered state

The accepted customer operations chain is:

```text
Customers
  -> find/create customer
  -> customer detail
  -> Overview / Commercial / Credits / Sites / Access / Audit

Service status
  -> find prioritized problem
  -> contextual customer, subscription, or site detail
  -> owning action
```

Current interaction decisions:

- customer Account ID is automatic and opaque;
- directory search is visually dominant over bounded filters;
- customer rows have one primary Detail action;
- package management exists only in Commercial;
- one Account state action is direct, not hidden in a one-item menu;
- low-frequency credit adjustment and destructive access work start
  disclosed;
- comparison data uses semantic dense tables;
- Customer and Service status remain separate navigation entries.

## 5. Development experience

### 5.1 Start with the operator question

The most important design move was naming the question each route answers.
Backend entities and shared customer IDs did not decide the navigation. The
operator job did.

For future Admin work, write before editing:

- question answered;
- default population;
- sort order;
- decision supported;
- action owner;
- completion condition.

If two surfaces differ on most of these fields, they should not be merged for
visual convenience.

### 5.2 Treat the absence of compatibility burden as a design input

The project had no customer population or historical frontend contract. That
made it correct to remove obsolete URL filters, a duplicate inspector, the
standalone Portal-users surface, and premature menu structure.

This does not mean durable domain boundaries should be collapsed. Principal,
Account, and Membership stayed separate even while the operator surface became
one customer workspace.

### 5.3 Stabilize interaction before extracting abstractions

The sequence was effective:

1. establish route ownership;
2. establish tab ownership;
3. simplify actions;
4. choose summaries, tables, forms, and disclosures;
5. reuse shared primitives;
6. add structural and browser guards.

Extracting a universal customer component before these decisions would have
encoded the ambiguity.

### 5.4 Density is semantic, not decorative

Reducing padding alone does not create an efficient Admin. Density improved
when:

- repeated options became rows with aligned columns;
- one current conclusion became a compact definition list;
- low-frequency mutation moved behind disclosure;
- duplicate actions disappeared;
- shared table framing removed nested card boundaries.

The table decision should be based on comparison, not on a desire to make the
page look “more professional.”

### 5.5 Accessible names are part of operational precision

An action labelled only `Apply package` is ambiguous when repeated in four
rows. Including `Free`, `Plus`, `Pro`, or `Agency` in the accessible name makes
the target explicit for assistive technology, tests, and operators.

Accessibility corrections frequently improve operational clarity for every
user.

### 5.6 Candidate, merge, and acceptance are separate

The layout first passed local and M4 candidate checks. It was not reported as
accepted until:

1. required GitHub checks passed;
2. PR #431 merged into `master`;
3. clean current `master` was promoted;
4. M4 status reported `acceptance_state=accepted`;
5. the accepted page was checked again.

A successful page on a feature branch is behavior evidence, not integration
truth.

### 5.7 Local preview availability is not service health

`http://127.0.0.1:18010` is a loopback SSH forward. The M4 service can remain
healthy while the local URL is unavailable because the foreground tunnel was
closed.

Closeout should state whether the tunnel remains open. The normal command is:

```bash
pnpm run m4:preview:tunnel
```

The command must remain in the foreground. It is not a permanent local server.

### What worked well

- The user challenged the initial merge hypothesis before implementation was
  frozen.
- The design used the lack of compatibility burden to delete obsolete UI.
- Durable Principal, Account, and Membership boundaries remained intact.
- Each follow-up PR narrowed one responsibility instead of reopening the whole
  Admin.
- Shared dialog and table primitives reduced route-local interaction code.
- Browser checks verified real tabs, labels, disclosures, and overflow.
- GitHub merge authority and M4 acceptance were kept separate.
- The original dirty worktree was preserved through isolated worktrees and
  exact staging.

### Next focus

1. Keep Customers a directory and Service status the only cross-customer
   problem queue.
2. Do not add a needs-action tab to Customers or another customer directory.
3. Apply tables only to real repeated comparison.
4. Keep one action owner and one primary action per section.
5. Repair stale operator-path assertions only in a focused test-maintenance
   change.
6. Revalidate current route evidence before any new customer-detail refactor;
   this closeout is a baseline, not permission for a broad rewrite.
