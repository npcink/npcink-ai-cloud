# Runtime 观测工作台改造计划 v1

状态：阶段 0-3 的首个实现切片已完成；阶段 4 真实场景验证待执行。

范围：`/admin/troubleshooting` 与 `/admin/usage-statistics` 的产品契约、
信息架构、跨页上下文和只读诊断体验。本文不授权计费产品、生产发布、
WordPress 写入或新的遥测采集体系。

## 已确认的产品决策

| 事项 | 决定 |
| --- | --- |
| 主要使用者 | Cloud 平台管理员和技术支持人员 |
| 第一版下钻粒度 | 支持进入单次运行摘要，并保留运行 ID 等证据标识 |
| 使用统计边界 | 运行观测和使用证据，不承担商业、计费、收入或留存分析 |
| 编辑效果 | 保留为低频专题入口；第一版不把它并入运行健康结论 |

## 页面分工

`/admin/troubleshooting` 是异常处置主入口，回答“哪里有问题、影响谁、
证据是否完整、下一步怎么查”。

`/admin/usage-statistics` 是趋势和分布入口，回答“运行量如何、来自哪些
站点/功能/插件、变化是否值得进入诊断”。

两页共享时间窗口、对象身份、数据新鲜度、样本完整性和跨页 URL 上下文，
但不合并为一个页面。使用统计发现异常后进入运行诊断；运行诊断应能回到
同一时间范围和对象的使用趋势。

## 分阶段交付

### 阶段 0：共同契约

统一 Runs、Plugin Events、Provider Calls、Metering、Editorial Outcomes
的含义；定义时间桶、时区、样本上限、缺失值、部分失败、数据缺口与运行
故障的表达；约定 `window`、`site`、`function`、`plugin`、`issue`、`run`
的跨页参数和返回上下文。

验收重点：同一事实在两个页面的名称、数字和限制说明一致；页面不会把
“没有观测证据”表述为“运行失败”。

### 阶段 1：运行诊断主工作台

保留结论、异常队列和 Inspector，但补齐站点、功能、最近发生时间、影响
运行数及单次运行摘要；区分运行故障与观测完整性缺口；让站点筛选和异常
下钻可以在页面内完成；把重要完整性状态移出低频抽屉。

验收重点：管理员可以从一个异常确认影响范围、查看匹配运行 ID、判断证据
是否完整，并获得明确的下一步入口。

### 阶段 2：使用统计趋势工作台

将 Cloud Runtime Runs、Plugin Activity Reports、Editorial Outcomes 分成
清晰的语义区域；增加有限搜索、失败优先排序和分页；显著展示截断样本、
耗时样本量和 pending 对成功率的影响；站点、功能和插件链接必须保留完整
上下文进入诊断或专题观测页。

验收重点：管理员可以判断变化是否来自真实运行、插件上报或测试记录，并能
一键带着对象范围进入诊断。

### 阶段 3：跨页闭环

统一跨页返回路径、对象命名和 partial-error/stale/sample-truncated 状态。
运行诊断提供回到同范围趋势的入口；使用统计提供进入对象诊断的入口；
关键路径用浏览器行为测试证明上下文没有丢失。

### 阶段 4：真实场景验证

至少验证三类场景：运行正常但无插件上报、运行失败且有 Provider 错误、
运行正常但 Provider Call 或计量记录不完整。验证页面结论、影响范围、
证据完整性和恢复判断，不以模拟数据或结构检查替代人工场景验证。

## 明确非目标

- 不把使用统计改造成计费、收入、留存或客户商业分析页面；
- 不新增通用日志平台、追踪系统或点击漏斗；
- 不把编辑效果直接并入运行健康结论；
- 不移动 WordPress 的设置、审批、最终写入或本地控制面真相；
- 不因为页面改造而新增供应商、路由、prompt 或运行配置写入操作。

## 交付与验证边界

每个阶段保持一个可审查的前端/Admin 改动切片，先运行最窄的行为与结构
门禁，再按页面模型执行 `check:admin-ui`；有布局、表格、Inspector 或共享
状态变化时执行 `check:admin-ui:visual`。跨页状态改变必须增加聚焦的
Playwright 行为证据。后端仅在现有投影无法表达“单次运行摘要”或筛选上下文
时，按独立 API 契约切片修改。

## 当前 API 事实与第一版约束

当前两个页面共用 `/api/admin/runtime-telemetry`，但它不是单次运行查询
接口。它按时间窗口和可选 `site_id` 读取运行、Provider Call、计量事件，
运行样本最多 5,000 条，诊断页面将 `limit` 设为 25，统计页面将其设为
100。`alert_summary` 最多返回 8 类异常，`capability_groups` 是聚合的
能力分组；现有响应没有提供异常对应的完整运行列表或分页游标。

因此阶段 1 的“单次运行摘要”不能通过浏览器端从聚合数据推导。若要实现，
应新增一个只读、站点边界明确的运行证据查询契约，至少支持：

- `window` 或 `since/until`；
- `site_id`、`capability`、`issue_code` 的受限筛选；
- 有界 `limit` 与稳定排序；
- `run_id`、站点、功能/能力、状态、开始/完成时间、受限错误代码；
- `has_more` 或游标状态；
- 明确的 `sampled`、`truncated`、`freshness` 元数据。

该查询只返回诊断所需的元数据，不返回 prompt、结果 payload、凭据或原始
Provider 请求。若后端暂时无法提供该投影，阶段 1 的验收必须标记为不完整，
不能用 capability 汇总冒充单次运行证据。

跨页参数的第一版约定如下：

| 参数 | 用途 | 归属 |
| --- | --- | --- |
| `window` | 24/72/168 小时范围 | 两页共享 |
| `site` | 站点范围 | 两页共享 |
| `function` | 能力/功能范围 | 统计页发现，诊断页消费 |
| `plugin` | 插件来源范围 | 统计页与插件观测消费 |
| `issue` | 诊断异常代码 | 诊断页 |
| `run` | 单次运行摘要 | 诊断 Inspector |
| `from` | 返回来源及返回上下文 | 跨页导航 |

参数只表达筛选和只读上下文，不改变 Cloud/WordPress 的所有权，也不构成
写入授权。

## 验证记录与后续验收

已完成的自动化证据包括 Admin UI 结构/视觉门禁、运行诊断 API 测试、单次
运行 Inspector 聚焦测试、Usage Statistics 聚焦测试，以及跨页 URL 上下文
断言。它们证明了契约和交互状态，但不替代 M4 上的真实数据观察。

阶段 4 的人工验收按以下顺序记录：

1. 正常运行但没有插件上报：应显示运行正常，同时标明插件观测缺失。
2. 运行失败且存在 Provider 错误：应能从异常进入匹配的运行 ID，并显示受限
   错误证据和下一步诊断入口。
3. 运行正常但 Provider Call 或计量记录不完整：应区分运行状态与证据完整性，
   不把缺失记录直接解释为运行失败。

每个场景需记录时间窗口、站点/功能范围、页面结论、运行 ID、样本截断状态和
返回路径；若数据不存在，记录“未观察到”而不是用结构测试代替真实证据。
