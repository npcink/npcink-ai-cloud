# Site Knowledge 推荐质量历史归纳与分阶段落实记录

Status: dated development synthesis (2026-08-26), not runtime or release authority.

Purpose: 将关于内链候选、相关文章推荐、向量质量、真实数据、AI 辅助评审和
第三方开源参考的历史讨论，整理成一份可复用的开发经验记录。运行时字段、
边界和限制以 [Site Knowledge Runtime Contract](site-knowledge-runtime-contract-v1.md)
为准；质量路线以 [Site Knowledge Recommendation Quality Improvement Standard](site-knowledge-recommendation-quality-improvement-standard-v1.md)
为准。

## 1. 先把两个功能说清楚

内链候选和相关文章推荐都可以使用 Site Knowledge 向量召回，但不是同一件事：

| 功能 | 解决的问题 | 主要判断 | 最终动作归属 |
| --- | --- | --- | --- |
| 内链候选 | 当前段落中的哪句话适合链接到哪篇文章 | 目标相关性、正文上下文、自然锚文本、当前编辑器状态 | WordPress/Toolbox/Toolkit 审核后 Apply、保存、发布 |
| 相关文章推荐 | 读者接下来可能继续阅读哪些文章 | 主题相关性、文章级去重、当前文章排除、主题覆盖 | WordPress 本地展示和编辑确认 |

共同点是向量负责主要语义召回，Cloud 可以补充只读证据和排序解释；不同点是
内链需要句子级锚文本安全门，相关文章不应返回同一文章的多个 chunk，也不应把
当前文章推荐给自己。不能因为两者都叫“推荐”就共用一套 UI、加分规则或 Apply 行为。

## 2. 历史上暴露出的主要问题

### 2.1 信息和按钮过密

早期界面把内链、相关文章、来源证据、操作按钮和低频解释放在同一层，造成：

- 同一信息在标题、标签、说明和详情中重复出现；
- 一个选项仍使用折叠容器，增加寻找成本；
- 忽略按钮没有明确说明它影响什么；
- 内容下面的操作按钮排列过紧，用户难以区分查看、复制、应用和忽略；
- Cloud 的排序细节被误认为 WordPress 的最终编辑动作。

落实的界面原则是：第一层只呈现候选标题、相关性摘要、来源和明确的三个主要动作；
低频诊断和排序解释放入详情；单一选项不折叠；“忽略”必须关联当前候选并说明是
隐藏/跳过本次建议，不等于删除文章、不等于修改模型，也不等于永久屏蔽。

### 2.2 “有向量”不等于“推荐一定正确”

向量能表达语义相近，但仍可能出现主题漂移、同文多 chunk、当前文章自荐、标题
看似相似但正文不适合作为内链等问题。关键词、标题和 taxonomy 只能作为召回后的
有界证据，不能取代向量，也不能在没有标签时宣称质量提升。

### 2.3 单人开发没有足够人工 gold

单个开发者很难一次整理 30 条完整人工 gold。因此要把“机制验证”和“质量结论”
分开：合成 fixture 可以验证排序边界、去重、自荐排除和指标计算，但必须保持
`insufficient_real_gold`；30 条完整人工 gold 是正式质量声明门槛，不是修复明显安全
问题的前置条件。

## 3. 已确认的架构边界

Cloud 负责：

- 向量候选召回、可选 Provider rerank、文章级合并和只读质量详情；
- 当前文章排除、结果来源和排序策略解释；
- 一次有界的 taxonomy/reference metadata 查询；
- Eval Lab 所需的候选顺序和质量证据。

WordPress、Toolbox 和 Toolkit 负责：

- 编辑器状态、正文匹配、自然锚文本安全门；
- 查看、复制、忽略、Apply、保存、发布和最终写入；
- 本地产品文案和用户确认。

Cloud 不应成为第二个 WordPress 控制平面、第二个 workflow/ability 注册中心、
最终审批或写入者。Cloud 返回的排序解释是诊断信息，不是自动写入指令。

## 4. 已落实的低复杂度改进

### 4.1 内链质量基线

- 保留现有向量候选池、当前文章排除、文档级 collapse 和可选 rerank；
- 内链在向量之后使用词面、主题和来源锚证据进行有界精排；
- 泛词、标题全文和不存在于正文的锚文本继续 fail-closed；
- Provider-rerank 分数和 vector 分数按来源分组，禁止跨尺度直接比较。

### 4.2 相关文章专属排序

相关文章使用独立策略 `semantic_plus_bounded_title_topic`：

- 语义分是主分；
- 标题共享词最多加 `0.04`；
- 分类/标签主题重合最多加 `0.04`；
- 本地证据总加分最多 `0.08`；
- 默认强制 `document` 粒度，截断前先去重；
- `current_post_id` 在向量路径和 PostgreSQL fallback 都排除；
- 返回 `related_content_ranking`，解释语义来源、两个 bonus 和最终排序分。

这组数值是保守的工程起点，不是经过真实用户数据校准的最优权重。

### 4.3 离线比较

Eval Lab 增加 `related_content_strategy_review.v1` 和
`related_content_strategy_comparison.v1`，比较 `vector_only` 与
`hybrid_evidence` 的已排序输入，输出：

- Precision@5、Recall@5；
- 重复率和自荐次数；
- Top-5 主题多样性；
- 无 gold 样本数。

Eval Lab 只测量传入顺序，不复制 Cloud 排序算法，不调用 Provider，不把合成数据
包装成线上质量证明。

## 5. 分阶段路线和停止条件

### 阶段 0：冻结基线（已完成）

记录现有召回、去重、当前文章排除、内链锚安全门和指标定义。目标是让后续变化
可比较，而不是马上追求一个漂亮分数。

### 阶段 1：相关文章小步优化（已完成）

只加入文章级去重、当前文章排除和有界标题/主题证据。复用现有向量路径和 metadata
查询，不增加向量库、搜索服务或新 embedding 模型。

### 阶段 2：小样本离线比较（已完成）

先用 10 条合成样本验证指标和明显边界，再逐步补到 10–20 条代表性案例。结果只用于
发现重复、自荐、主题漂移和策略解释问题，质量状态保持不足真实 gold。

### 阶段 3：真实使用观察（待办）

积累至少 20 次相关文章/内链曝光，再人工抽查 5–10 个打开、采用、编辑、忽略或撤销
案例。观察数据只能作为弱反馈，用于站点内的 before/after 诊断，不能自动改全局权重。

### 阶段 4：正式质量比较（待办）

真实数据足够后，建立独立人工评审集。正式质量声明需要正好 30 条完整样本，每条有
`annotator` 和 `reviewed_at`，并分别比较相关文章与内链的 Precision@5/Recall@5。

### 阶段 5：模型或 LTR（暂不启动）

只有当阶段 3–4 明确证明现有向量加有界证据仍有稳定瓶颈，才考虑 RRF、cross-encoder、
Learning-to-Rank、换 embedding 或多 AI 评审编排。没有瓶颈证据时，这些方案只会增加
成本、运维面和解释难度。

## 6. 多 AI 和开源项目的正确用法

不同 AI 可以作为离线评审者，而不是互相“训练”。当前 MVP 只启用 GPT 和
Grok：两者独立输出相关、重复、自荐、主题漂移和锚文本安全标签，再由确定性
聚合器保留通过、拒绝、弃权、Provider 错误、无效 JSON 和分歧。平票或边界失败
转人工确认，不平均不同 Provider 的原始分数，也不因为评审者数量不足而引入第三
或第四个模型。只有当 GPT/Grok 的分歧在足够真实样本上持续且现有规则无法解释
时，才重新评估增加模型的成本和收益。

第三方开源项目可参考混合检索、RRF、cross-encoder 和隐式反馈去偏等机制，但采用
前必须检查许可证、分数语义、中文分词、数据传输、成本和回滚路径。不能因为某个
项目成熟，就在现有 Cloud 之外再建一个搜索控制平面。

## 7. AI 特色图的提示词和传输经验

AI 特色图不是“直接把一段英文塞进文本框再生图”的功能，而是一个需要人工确认的
两层提示词流程：

1. 中文“画面描述”是用户可读、可编辑、可确认的主字段，应该先有它，再显示生成
   方向、比例、质量和请求按钮。
2. 英文模型提示词是 Cloud/Provider 的执行稿，默认放在“高级信息”中，不应覆盖主
   字段，也不应在方向切换或重新生成时把英文写回中文文本框。
3. 用户修改中文描述后，Cloud 负责按请求翻译；用户未修改已有提示词对时，可复用
   已配对的 Provider prompt。翻译状态和 Provider prompt 是否被人工审阅必须单独记录。
4. 请求、生成、拉取、校验、ACK 是不同阶段。遇到“生成失败”时，先区分 Provider
   执行失败、Cloud artifact 过期/拉取失败、签名或 checksum 校验失败，以及 UI 旧状态
   串显示，不能一律归因于向量或模型质量。
5. Cloud 返回的 UTC 时间戳只接受规范的 `Z` 和字面量 `+00:00` 两种编码；不放宽到
   任意偏移、无时区或宽松日期解析。这样能兼容真实返回值，同时保持边界可验证。

生图界面应在请求期间禁用方向和模式切换，按当前模式渲染候选，避免旧的站内媒体
候选或“未找到图片来源候选”覆盖生图状态。相关错误要告诉用户下一步动作，并保留
可诊断的 Cloud 状态，而不是展示含糊的 Provider 原始错误。

## 8. 可复用的开发经验

1. 先追完整调用链，再改 UI：零结果可能来自请求校验、Connector 投影、Cloud 查询
   或渲染状态，不能默认是向量问题。
2. 先处理确定性安全问题，再调权重：自荐、重复、标题全文锚和正文不匹配比“整体
   相关性可能略低”更适合先修。
3. 复用现有边界：只在拥有排序真相的 Cloud 做排序，不把语义去重复制到 WordPress。
4. 所有本地 bonus 必须有上限、可解释、可回滚，并配套近分和大分差测试。
5. 不同 Provider 的分数不天然同尺度；使用来源分组或 rank-based 方法，不做裸分比较。
6. 合成数据用于发现机制缺陷，真实人工数据用于质量声明；两者在字段和状态上必须
   明确区分。
7. 单人项目要设置停止线：当新增复杂度不能回答当前问题，就先积累真实使用证据。
8. 每次修改都记录 focused test、静态检查、运行时状态和未完成项；“测试通过”不能
   被写成“推荐质量已提升”。

## 11. 当前停止线

在单人项目中，先维持小闭环：三类证据（合成 fixture、GPT/Grok silver、真实行为）
分开存放和解释；达到 20 次 impression 前不宣称稳定率，不从一次点击或一次保存
自动调权；没有持续、可复现且规则无法解决的瓶颈，不增加第三模型、向量数据库、
新队列、复杂模型路由或自动写入机制。
