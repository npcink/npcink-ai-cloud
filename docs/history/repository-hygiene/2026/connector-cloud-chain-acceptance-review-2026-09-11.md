# 连接器到 Cloud 调用链验收调查（2026-09-11）

## 目的

核对 WordPress 插件、连接器与 Cloud 运行时之间是否已有可定位的调用证据。本文只做只读调查，不修改 `ai-wp-admin`，不记录正文、提示词、结果或凭据。

## 当前证据

| 环节 | 已有证据 | 当前管理员入口 |
| --- | --- | --- |
| 插件发起 | Cloud 侧存在插件观测事件汇总与站点维度统计 | 使用统计、插件观测 |
| 连接器转发 | 运行请求/结果封装包含 `run_id`、连接器结果信封和错误码 | 运行诊断中的运行记录 |
| Cloud 接收 | 运行记录、终态回调、结果规范化和幂等错误码已存在 | 运行诊断 |
| AI 服务调用 | 使用统计保留成功率、耗时、错误码等元数据 | 使用统计、资源观测 |
| 返回结果 | 运行结果查询、临时结果和结果未就绪/过期错误已定义 | 运行详情 |

## 仍需确认的链路字段

现有页面能看到运行或插件事件，但尚未在一个管理员视图中明确串联：插件来源、连接器请求是否到达、Cloud 处理阶段、上游失败阶段。下一步应先用一次真实调用核对这些字段是否在同一 `run_id` 或关联标识下可追溯。

## 最小验收步骤

1. 从 `ai-wp-admin` 发起一次非敏感测试调用。
2. 在 Cloud 运行诊断按时间窗口查找对应运行记录。
3. 在插件观测查找同一站点/插件事件。
4. 对照请求是否到达、终态、耗时和错误码。
5. 若无法串联，再只新增缺失的关联字段或展示入口。

- 来源：本地 `ai-wp-admin` 编辑页
- 调用类型：编辑辅助能力

## 结论

Cloud 已具备分散的运行、插件观测和结果证据，当前主要缺口是管理员无法用一条链路快速判断失败发生在哪一层。先完成一次真实调用的关联核对，再决定是否需要实现改动；标题格式等插件体验问题另行处理。

本轮候选扩展管理员 plugin-observability 摘要（原有鉴权不变）：

- 新增 recent_activity，按 received_at、id 倒序取最多 50 条，沿用时间、站点、插件和测试记录过滤。
- recent_activity_limit 固定为 50；这不是完整历史或分页接口。
- 每项 run 为 null 或包含 run_id、status、started_at、finished_at、error_code 的只读摘要。
- 仅当 correlation_id 精确匹配同站点 run_id 时关联，不猜测时间邻近关系，不跨站点串联。
- 保留 recent_errors 及现有统计语义；普通门户摘要不新增此字段。
- 不暴露请求、结果、提示词、凭据或完整 payload；查不到运行不等于调用失败。
- 管理员从“近期上报”展开“查看对应运行”，比较实际执行与接收时间；无需另开诊断页。
