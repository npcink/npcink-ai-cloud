## 2. 讨论主线与关键取舍

### 从界面美化转向用户任务与可信状态

最初审查覆盖登录、首页、站点详情、套餐/积分购买、用量、工单、账户和最近活动。
问题包括信息重复、动作竞争、工单筛选与实际查询不一致，以及请求失败仍显示
绿色正常或零值。整改围绕“看懂当前状态 → 一个最佳下一步 → 必要记录 →
低频细节”，没有另建厚重客户控制台。

账户拥有套餐、积分和商业证据；站点拥有连接、运行和诊断。筛选站点不应改变
商业账户，站点连接状态与服务健康也不能混为一谈。Cloud 执行托管任务和显示
证据，WordPress 保留能力/提示词/审批与最终写入。

### 从页面可用转向业务与性能可验证

Portal #1079/#1080/#1081 完成查询边界、操作简化与状态收口。10 月 8 日记录
包含 33 项浏览器用例、8 项隔离 PostgreSQL 写入/并发场景及迁移恢复证据。
当时用量汇总样本约 9.8→0.30 秒、最近活动约 5.9→0.08 秒；这是历史样本，
不是今天重测或持续性能承诺。

后续 #1083 修正导航归属，#1086/#1087 收口后台诊断及跨平台测试，#1088 优化
用量健康读取，#1090 为活动读取增加请求引用和失败恢复。历史 F8 原故障没有
原始响应，不能因当前成功或加入注入失败测试就宣称历史根因已证实。

### 把销售价格、用户积分与 Provider 成本分开

用户讨论过赠送、补偿、加购积分是否需要联动人民币成本预算。最终方向是：

- 用户按积分和有效期理解权益，赠送/补偿等通过已有账本处理；
- 套餐销售价格独立，套餐级成本阈值仅作内部监控，放入高级披露；
- Provider 账户预算是独立的日/月 USD 调用保护，默认 80% 预警，达到上限拒绝
  新 claim，不通过中断已开始请求制造“封顶”效果。

#1092 已补齐预算设置界面及投影。历史回答曾误称入口已经存在，随后在原会话中
纠正并实现；不能沿用早期“还没有入口”的判断，也不能因实现合入就声称生产
开关、实际数值和所有付费旁路都已覆盖。以实际启用路径逐一核对，保留未知项。

### 固定小样本试用规则，后移收费和扩张

操作者确认的规则是 300 AI credits / 30 天，不新增周限额；首批 3 位熟人站长，
第一周观察后再决定是否扩到 5 位；正常自注册，不建立邀请码后台；不付款、不
充值、不自动转收费。T+0 是准备完成后的实际邀请日，不是文档日期。

四周沿用 H1 采纳/展示 ≥40%、H2 两周留存 ≥50%、H3 单活跃用户月成本
≤¥5–7 的既定判据。平台实际账单是成本侧证据，run/反馈是行为侧证据；
`accepted_rate` 的反馈分母不能冒充展示分母，缺失事件也不能当拒绝。
这些判据是观察计划，不是已经得到的商业结论。

### 从生产失败中修正发布与 Provider 的边界

会话记录了发布准备、证书 readiness 记录过期、RDS 连接拒绝、SSH bundle
验证依赖缺失，以及迁移后 Provider 401 令服务 fail-closed、公共请求出现 502。
这些是相应时点的历史故障，不代表目前仍故障。

操作者指出 API key 会过期，不能让一个可运维配置问题决定整个应用是否可发布。
#1115/ADR-059 于是允许既有历史 catalog 时按发布策略保留投影并报告 degraded；
运行时请求、首次无目录安装、持久化和其他关键失败不因此变成成功。有效 key
仍须通过 Admin 管理，目录连接测试不等于内容生成或实际质量验证。

### OCR 保持有预算的第二意见

原会话区分本机 CLI 与 GitHub Runner，二者都会调用远端模型，并不是本地模型
服务。GLM 429、资源包不足、千问审查前预算不足、空审查和后来的启动故障必须
分别诊断。#1106/#1108 等已收紧触发、并发、重试与预算；当前政策为单并发、
low、80,000 token 软预算。#1122 禁止固定 CLI 启动期间自更新。

历史模型选择与同行产品对比属于当时讨论，不作为本纪要的当前外部产品推荐。
OCR 部分/失败结果仍是不完整证据，不替代确定性检查、合并保护或生产授权。

### 把逻辑缺陷前移，生产保留必要人工验证

生产使用暴露“保存后仍显示测试中”：临时提示未清除，刷新又覆盖错误。先修
结果顺序，再统一成带上下文 key 的 `idle/running/success/failed`；还发现目录
同步成功却未写 success 的相邻问题。测试重点由截图扩展到成功、失败和刷新
后的最终状态。#1117 已把该实现合入 master。

随后提出零付费关键流程验收包与 `verify:local-critical`，但相关回合中断，当前
package.json 没有该命令。方案中的“本地 Docker”也不能照搬：当前工作模型
规定 Mac 负责源码/静态检查，Cloud Docker、数据库及集成运行归 M4。

## 4. 当前会话旧摘要的校正与交付恢复

10 月 16 日当前会话写入了历史摘要 `71017e23` 和生产清单 `867ebcb4`，但当时
只本地提交，未发布/合入。本次发现旧附属 worktree 路径已不存在，当前 master
也没有两份文件；Git 对象仍可读，故按精确对象恢复，未从记忆重建或假称已入库。

原摘要错误地把引用会话的准备回合当成最后结果，写成“等待 `982b132d` 部署
授权”；完整后续和成功工作流已否定这个判断。恢复稿顶部有校正，旧 SHA 不应
再被作为待部署任务。#1117 也从早期本地候选进入了当前 master/production。

生产清单同时修正两点：内部 run/预算/反馈证据由开发侧核对，不把技术诊断
交给普通操作者；区分 AI 未经采用写入、人工采用进入编辑器与 WordPress 草稿
自动保存。首次一次真实 smoke 也不冒充原六条清单的全部验收（其中有不少于
10 次真实使用要求），后续应自然积累。

## 5. 下一阶段：双轨推进，先完成一个可用闭环

### 开发侧先做：把已知故障变成便宜、可复用的回归证据

下一项建议任务聚焦验证编排，不顺带大改后台：先盘点已有验证命令与 fixture，
再决定扩展 `verify:local` 的明确 profile，还是增加独立关键流程入口，避免
重复命令和隐藏的 Docker/M4/付费动作。这是下一任务建议，本轮不实现。

最小覆盖应复用已知缺陷：Provider 保存后成功/失败、目录同步终态、刷新不吞
错误、Portal 注册登录与 Free、账户/站点边界、读取失败与重试。Mac 先做类型、
lint、纯状态/合同及合适的 Mock 浏览器测试；真实容器、PostgreSQL 和跨服务
smoke 在 M4 有界执行。输出明确的 passed/failed/skipped 与版本；缺运行前提
应报告缺失，不静默绕过或启动本机 Cloud Docker。

完成目标：有可重复执行的零付费回归清单，能在发布前稳定重现并拦截已知逻辑
缺陷。它不保证所有问题都能在生产前发现，也不替代真实邮件或 Provider 验证。

### 操作者并行做：按清单验证真实生产体验

沿用[生产邮箱与写作清单](../../../portal-production-validation-runbook-2026-10-16.md)：

1. 生产正常邮箱注册、收件、验证与退出重登，核对 Free 和无站点状态。
2. 从 WordPress Addon 连接测试站，确认 Portal 站点显示一致。
3. 实际预算已启用且覆盖所选 Provider 后，用非敏感草稿完成一次标题建议，
   人工采用、保存和回读。不要用真实超限、重复点击或批量调用测试保护。
4. 只回传是否完成、时间、前后积分与一个卡点；密钥/验证码/Cookie/正文留在
   自己环境。开发侧补查 run、实际模型、成本与原生反馈；不为取引用重做生成。

本轮没有收到这些动作完成的反馈，不要求重新授权旧部署，也不要求操作者
把 Admin key 提供给 AI。formal smoke 如需接续，须依现行流程另作受保护配置。

### 闭环通过后：邀请 3 位站长，再决定下一笔投入

先复核六条 Done 的已知/未知、告知及页脚，记录匿名 S1–S3 与受控映射。
准备完成才记 T+0，每周一份事实记录，四周后按 H1/H2/H3 判断达到、未达到或
无法判断，给出 go/modify/hold/stop。不把一次内部 smoke 变成商业验证完成。

优先修权限/隐私/数据丢失和连接、生成、恢复、保存阻塞；重复困惑其次。
支付、复杂邀请/周限额、通用分析后台、全站视觉重构和新能力暂不扩张。
已确认的上游安全例外在 10 月 25 日到期前须另立维护任务核对，不借本文
续期、不混入体验任务或启动新部署。
