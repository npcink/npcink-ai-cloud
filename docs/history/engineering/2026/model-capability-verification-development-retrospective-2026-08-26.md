# 模型能力发现与验证阶段复盘 - 2026-08-26

Status: dated development retrospective; not merge, M4 acceptance, production,
or product-quality authority.

## 1. 背景

本阶段从一个具体问题开始：模型资料显示 GPT-5.4 支持视觉输入，但在 Cloud
的运行配置中无法作为“图片 ALT 视觉”候选。继续为每个新模型手工写死能力
既不可持续，直接相信模型名称或第三方目录也无法证明当前 Provider 网关真的
转发了图片、向量或媒体请求。

随后问题扩展到向量、图片生成、音频生成和视频生成。项目的现实约束是：

- 当前主要由一名开发者使用，真实数据少；
- Provider 调用可能付费，不能批量制造观察数据；
- Cloud 是托管运行增强层，不能成为第二套 WordPress 能力或工作流控制面；
- 项目仍在开发中，不需要保留错误的兼容路径；
- 优先完成收益大、复杂度小、能形成闭环的能力。

## 2. 核心决策

最终采用的判断链路是：

```text
官方/第三方资料
  -> 发现能力候选
  -> 验证当前 Provider + 模型 + 端点 + 请求格式
  -> 保存带路由指纹的能力证据
  -> 决定配置保存和真实运行资格
```

外部资料回答“可能支持什么”，真实探测回答“当前这条路由能不能用”。两者
不能相互替代。LiteLLM、models.dev、OpenRouter 等资料可作为参考来源，但
不因为目录里出现 `vision=true` 就将实例标记为 `verified`。

## 3. 已形成的能力闭环

截至本记录对应的开发候选，已经形成以下机制：

- 统一状态：`unverified`、`verified`、`unsupported`、
  `verification_failed`；
- 统一证据键：Provider connection、模型、能力、端点和请求格式组成路由
  指纹；
- 视觉探测：固定小图片和固定问题，要求得到实际文本输出；
- 向量探测：要求非空、有限数值向量；
- 图片探测：要求图片字节、MIME 和解码有效，并复用 URL/SSRF 防护；
- 音频探测：要求 Base64、大小及 MP3/WAV 基本格式有效；
- 配置门禁：视觉、图片和音频候选只有当前 `verified` 证据才能保存；
- 运行门禁：即使配置曾经保存，证据失效后也不能继续进入真实路由；
- 证据有效期：内部开发阶段为 30 天，路由变化会更早失效；
- 成本控制：新鲜成功证据直接复用，不重复调用 Provider；失败证据仍可人工
  重试；
- 低敏审计：记录能力、状态、实例、路由指纹、错误码和时间，不保存提示词、
  图片、音频、密钥或原始 Provider 响应；
- Admin 观察：运行配置页通过默认折叠入口展示最近窗口、尝试数、成功率、
  按能力统计和最近错误，不挤占日常配置工作区。

视频生成仍保持 `unverified`。原因不是模型目录缺少“视频”标签，而是当前
Provider adapter 尚未具备可验证的“创建异步任务 -> 查询状态 -> 获取完整
视频工件”合同。在实际 Provider 路由确定前，不应伪造一个只验证任务受理的
成功状态。

## 4. 为什么观察成功率和错误分布

这组观察回答的是：

> 选中的模型通过当前 Provider 路由，能否稳定完成这类调用？

各能力关注点不同：

| 能力 | 观察目的 |
| --- | --- |
| 视觉 | 图片是否真的被接口接收并产生可用理解结果 |
| 向量 | 是否稳定返回合法向量，而不是空值、NaN 或错误形状 |
| 图片生成 | 是否返回可获取、可解码的真实图片工件 |
| 音频生成 | 是否返回可识别、大小合理的真实音频工件 |

错误分布用于区分：明确不支持、认证错误、额度不足、限流、超时、网络故障、
返回空内容和无效工件。这个区分能指导换 Provider、调整超时、修 adapter 或
稍后重试，避免把基础设施故障误判成模型能力缺失。

## 5. 它不能说明什么

能力探测成功率不是模型训练数据，也不是内容质量评分：

- 视觉成功不代表 ALT 描述准确；
- 向量合法不代表相关文章排序相关；
- 图片能解码不代表文图对题或审美合格；
- 音频能播放不代表发音、节奏和内容自然；
- 超时或额度不足也不能证明模型语义质量差。

真正的质量改进需要另一条反馈闭环，例如推荐曝光、点击、采纳、忽略、替换、
人工修改和最终结果。两条数据可以联合诊断，但不能混成一个分数：先证明路由
可靠，再讨论输出是否有用。

## 6. 单人开发阶段的执行方法

当前选择“正常使用并自然积累”，而不是要求开发者人工完成固定数量的付费
探测：

1. 正常配置并使用视觉、向量、图片和音频功能；
2. 只有选择未验证、过期或路由变化的候选时才探测；
3. 新鲜成功证据直接复用；
4. 出现真实失败时查看错误码和同类重复情况；
5. 证据很少时只做个案诊断，不发布成功率基线或 SLA；
6. 有稳定重复模式后，再调整 Provider、超时或适配器；
7. 内容质量继续使用各功能自己的行为反馈和人工复核数据。

这里不要求“先凑够 20 次”才能处理明显错误。一次确定性的格式错误可以立即
修复；只有成功率、Provider 优劣和策略调整等统计判断才需要更多自然样本。

## 7. 开发经验

### 7.1 先分清模型、Provider 和路由

“GPT-5.4 支持看图”是上游模型事实，不等于某个兼容网关、部署实例和请求格式
支持看图。能力证据必须绑定完整路由，不能只绑定模型名称。

### 7.2 发现与准入必须分层

第三方目录可以减少人工整理成本，但不能成为运行准入真值。将外部资料限制为
候选发现，既避免逐个模型预先测试，也避免盲目信任营销标签。

### 7.3 成功响应不等于能力成功

媒体能力必须验证工件本身；向量必须验证数值；视觉必须验证实际输出。只看
HTTP `200` 会把空响应、错误 URL 和无效媒体当成成功。

### 7.4 临时错误不能变成永久封禁

超时、网络、认证、额度和限流属于 `verification_failed`，应允许重试；只有
Provider 明确、稳定地拒绝该能力时才使用 `unsupported`。

### 7.5 安全门禁不能抹掉诊断信息

保存和运行只接受新鲜 `verified` 证据，但 Admin 仍应展示当前路由的新鲜失败
证据及错误码。否则用户只看到“待验证”，无法判断应该重试、补额度还是换
Provider。

### 7.6 观察面应服务决策，而不是制造仪表盘

单人内部阶段只需要默认折叠的 attempts、verified、failed、能力分组和最近
错误。不要提前增加告警平台、自动排名、复杂时间序列或第二套注册表。

### 7.7 验证状态必须贯穿到真实运行

只在配置保存时检查不够。证据可能在保存后过期，运行时必须再次 fail closed，
否则 UI 显示的安全规则与真实调用行为会分叉。

## 8. 当前停止线与后续触发条件

当前阶段不继续扩展：

- 自动批量探测全部模型；
- 根据少量样本自动给 Provider 排名；
- 用多个 AI 相互“训练”制造真实用户偏好；
- 引入 LiteLLM、Temporal、Celery、Kafka 或第二套模型注册表；
- 在没有实际异步 Provider 合同前实现视频“已验证”。

后续在以下条件出现时重新评估：

- 某能力出现重复且可归类的失败模式；
- 有足够自然调用，需要比较 Provider 稳定性；
- 选定一个真实视频 Provider，需要实现异步任务和工件生命周期；
- 产品质量反馈积累后，需要联合分析“路由成功但用户不采纳”的问题；
- 进入更多用户阶段，需要调整 30 天有效期或增加明确的 Provider 预算控制。
