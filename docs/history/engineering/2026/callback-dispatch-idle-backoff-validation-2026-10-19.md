# 回调签名与空队列退避验证 — 2026-10-19

Status: dated engineering evidence, not production authorization or a capacity SLA.

## 问题与选择

上一轮签名复用候选减少了重复 PBKDF2 派生，但队列更快排空后进入原有固定 5 秒空轮询，回调尾延迟反而升高。本轮把签名复用与 worker 退避组合验证，不能直接把上一轮仅核心派发器的绝对值与本轮完整 worker 混为同一对照。

回调仍由 Cloud 托管 runtime 负责；没有引入 WordPress 写入、注册表或控制面归属变化。

最小实现为：

- 显式派发批次内最多复用最近一个相同 site/key/secret 指纹对应的派生密钥；批次结束或异常即清理。注册信息和目标仍逐次读取、校验，轮换即时失配；每次重新构建签名，不缓存请求头、时间戳或签名。
- 刚处理过回调后，第一次空队列等待 250ms，随后连续为空时倍增；默认 5 秒配置对应 0.25、0.5、1、2、4、5 秒，之后保持上限。正批次继续立即排空。
- 冷启动和长期空闲保持原配置等待上限。自动修复按单调时钟独立限频，最多每个配置周期执行一次，避免快轮询放大维护查询；心跳仍逐轮检查自己的既有记录间隔。
- 保留现有注册、幂等、计量、扣费、重试、失败状态、时间戳及提交语义。没有新 Redis 通知、监听连接、迁移、依赖或公开配置项。

选择有界退避是为了保持变更可回滚，并保留长期空闲成本。没有选择永久 250ms 轮询或新增通知基础设施。本轮没有解决冷空闲首条回调的最坏等待：轮询上限仍由原配置决定，默认约 5 秒，另加查询、签名和网络处理时间；不能声称实现了实时唤醒。

## 可复核条件

基线干净 master：`5fa1d47ca356b84ad767003315749890c2f412ab`；组合候选 runtime 源码：`ed2908671c84ac45e87cbe4bd74b486ad7f45a23`。后续只追加本记录和文档索引，runtime 源码不变。两版复用相同不可变运行时、PostgreSQL 和 Redis 镜像，并验证生产 Python lock manifest 匹配；不冷构建镜像。

M4 使用蒲公英 SSH，在主操作锁和测试槽均空闲后，分别运行私有六容器、网络和数据库：总硬 CPU 配额 2 核，API0.4、callback0.25、rollup0.25、control0.1、PostgreSQL0.9、Redis0.1。准备阶段 callback 也至少0.25核。各角色实际连接池均为 size2+overflow1。

每版三轮四路闭环请求，每轮80正式、4预热、2幂等重放，Provider 固定500ms且零付费。每轮固定一次 usage_rollup，实际启动落在非空回调批次内并与业务请求重叠。使用真实 callback worker 主循环、自动修复和心跳；接收器 MockTransport 独立校验 HMAC。两版共480正式请求，连预热共504个唯一运行。

另有每版60秒冷空闲、每轮业务完成后的20秒空闲、80次每8条一组的纯 HTTP 签名探针。第一正式派发统一延迟3秒是对照夹具，停止控制和探针也属于夹具，不能当作生产 worker 的延迟或 CPU 基线。

每轮回调 P95（基线→候选）分别为2562.5→1848.7、2381.6→1951.7、2541.8→1816.8ms。冷空闲两版均维持5秒等待；业务后空闲均回到约5秒间隔，候选平均多约0.00036核及每20秒多2–3条SQL。自动修复没有随快轮询倍增。

候选达到预先规定的空闲预算：冷空闲平均不超过0.025核、相对增量不超过0.005核；业务后空闲增量不超过0.01核。业务请求 P95 的3.6%上升必须保留，不据此声称提高业务吞吐。三轮只能说明方向，不能当作统计显著性或生产容量证明。

CPU 分段是嵌套线程计时，派生属于 headers→HTTP→batch 内，不能相加。批次 CPU 包含正式请求后的排空和20秒空闲尾段；硬限流比例仅对应正式业务窗口，两者时间口径不同。

## 正确性与验证

480次正式请求均成功，客户端和连接池超时均为0。两版每版252个唯一运行、1764条计量事件、504条账本记录和252个已送达回调，数值完全一致；六轮均验证一次503重试的稳定 callback ID、两次幂等重放和签名。Provider 等待期间未占数据库连接，正式请求仍为72条SQL和8次连接持有；没有改池大小。

本地35项定向/入口测试、`verify:local`（32项改动测试及选定静态/政策检查）、全仓Ruff和改动应用文件mypy通过。M4基线32项、候选43项通过。PR仍须经过实际选中的 GitHub required checks，完整后端 lane 被跳过不能称其已通过；本记录不提前声称合并或 accepted。

两版隔离运行合计734.683秒，低于1200秒预算。两份导出各142文件逐一SHA256校验后，才清理本任务远端scratch；私有容器、网络、卷及操作锁已释放。保护检查确认实验期间其他运行容器、共享部署标记、Ollama归属/PID和健康状态未变。没有付费业务Provider调用或生产操作。

## 后续验收与回滚

发布到 master 的 PR、required checks、干净 master 的 M4 promotion/status 与相关 smoke 是后续独立证据。候选同步不等于 accepted，M4 accepted也不等于部署生产。合并后以PR、当前master和M4 source revision三者绑定验收。

回滚采用单独审查的 revert PR，同时撤回签名复用和退避调度，再按当前master做M4 promotion；不在M4或生产直接改源码。连接池继续2+1，回调预算继续至少0.25核。多站点密钥交替、真实网络、冷空闲首条请求延迟和Linux容量仍需独立验证。
