# CPU 分配对照与性能专项收尾 — 2026-10-19

性质：历史实验与决策记录，不是当前运行配置、生产容量承诺或发布授权。

## 结论与目标

本轮不采用 API0.6 / PostgreSQL0.7 核的新分配，结束本次性能专项。
保留此前已合并的数据库连接释放、usage_rollup 和回调成本优化；不继续
搜索其他 CPU 比例，不因本轮结果扩大连接池或删除功能。

专项的目标是在 2 核 4GB 的目标预算下提高主业务的稳定并发，兼顾用量统计
和回调。减少后台 CPU 开销是手段，业务、回调和统计同时达标才是采用依据。
后续重心回到正常 WordPress Ability → Addon → Cloud runtime → 模型执行
→ 人工审阅采用的真实闭环及自然使用证据。

本轮是同一份源码的资源分配 A/B 对照，不是代码修复前后对照。上一轮
[回调签名与空队列退避验证](callback-dispatch-idle-backoff-validation-2026-10-19.md)
记录的业务 P95 为 681.994 → 706.494ms；其采样夹具与本轮不同，不能把
那两个绝对值与本轮结果拼接，归因于某一次代码变更。

## 固定条件与采样校正

实验冻结干净 master `7cd70adcb3dc508828625f13ada6469578c2c6ac`，
两组复用相同不可变 runtime、PostgreSQL、Redis 镜像，并校验 Python
依赖锁身份；零镜像构建、零付费 Provider 调用。

M4 操作锁和前端租约空闲后，经操作者选择的蒲公英 SSH 直传运行。六个
独立容器、私有网络和数据库只承载合成数据，不替换共享预览。

| 角色 | A 基线 CPU 核 | B 对照 CPU 核 |
| --- | ---: | ---: |
| API | 0.40 | 0.60 |
| callback | 0.25 | 0.25 |
| usage_rollup | 0.25 | 0.25 |
| control（客户端与观测） | 0.10 | 0.10 |
| PostgreSQL | 0.90 | 0.70 |
| Redis | 0.10 | 0.10 |
| 合计 | 2.00 | 2.00 |

各数据库使用角色的连接池均为 size2 + overflow1；准备阶段 callback
也至少0.25核。切换分配先减后增，避免瞬时超出总配额。六容器内存上限
合计2368MiB，不包含完整前端、代理及其他 worker；这不是全栈4GB验收。

- 数据固定为150万条健康历史、251个实例、5个站点，每格从相同模板克隆。
- 四路闭环请求，Provider 固定等待500ms；真实 callback worker 主循环、
  维护与心跳保留，MockTransport 接收器独立校验 HMAC。
- 每格先做24次四路预热，再做80次正式请求及2次幂等重放。三种场景各三次
  配对，共18格、1440次正式请求、1872个含预热的唯一运行。
- 场景为无 rollup、首个业务请求开始时 rollup 已运行、非空回调批次内启动
  rollup；有任务的每格固定一轮，并验证任务与业务或非空回调的实际重叠。
- 第一、三次配对按 A→B，第二次按 B→A。保留同一正式首批回调3秒屏障；
  它是测试夹具，不能当成生产 worker 的固有延迟或回调 SLA。
- 删除每批回调后的额外 pending-count 观测 SQL；预热匹配四路并发，区分
  真实进入 `Condition.wait` 的等待与允许阻塞的 `Queue.get` 调用。
- PostgreSQL 由其独立容器内的常驻 shell 约每100ms读取 cgroup 计数，
  `/proc/uptime` 与同机 Python `CLOCK_BOOTTIME` 对齐。采样开销计入 PG
  预算，两组相同；实际平均采样间隔约102ms。

首个先导格被完整性闸门拦截：24预热+80正式+2重放超过默认每 key 90次/分钟，
后续请求返回429；镜像 BusyBox `date` 又不支持所用的亚秒格式。该格保留在
失败证据中，不计入正式对照。仅修正夹具：两组隔离设置统一为有界120次/分钟，
限流检查仍启用，并修正时钟来源，然后完整运行一次固定矩阵。没有修改应用
默认限流或共享配置，也没有选择性重跑表现不佳的格子。

## 执行前冻结的采用门槛

1. 三种场景的汇总业务 P95 以及各次配对均改善至少10%，体现稳定收益。
2. 各场景的汇总回调 P95、配对回调 P95 相对变化中位数均不增加。
3. 有 rollup 的场景，其平均任务耗时及配对耗时相对变化中位数均不增加；
   条数、统计语义、计量和回调完整性保持不变。
4. 正式请求全部成功，无客户端或连接池超时；幂等、扣费、签名和重试校验通过。

回调延迟从 API 终态 COMMIT 确认至接收器204计时；业务延迟为客户端完整请求
耗时。分位数采用 nearest-rank：汇总 P95 从每组每场景240次正式请求计算，
不是三次 P95 的平均；统计平均耗时每组每场景只有三轮任务。
所有条件同时满足才采用，不在结果出来后更改门槛。

## 业务结果

以下耗时单位均为毫秒；正的改善率表示对照组更快。

| 场景 | A 汇总业务 P95 | B 汇总业务 P95 | 汇总改善率 | 三次配对改善率 |
| --- | ---: | ---: | ---: | --- |
| 无 rollup | 710.584 | 689.607 | 2.95% | 4.83% / -2.82% / 3.03% |
| 请求开始时运行 rollup | 729.246 | 671.690 | 7.89% | -3.21% / 12.02% / 10.55% |
| 回调活跃时运行 rollup | 804.371 | 688.232 | 14.44% | 15.54% / 12.47% / 9.33% |

无任务和任务起始场景的汇总收益低于10%，且部分配对变慢；回调活跃场景的
汇总收益超过10%，但第三次只有9.33%。三种场景均未通过稳定业务收益门槛。

## 回调与统计结果

| 场景 | A 回调 P95 | B 回调 P95 | 回调 P95 变化 | A rollup 平均耗时 | B rollup 平均耗时 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 无 rollup | 2050.852 | 1943.679 | -5.23% | 不适用 | 不适用 |
| 请求开始时运行 rollup | 1894.494 | 1911.756 | +0.91% | 1069.187 | 1025.490 |
| 回调活跃时运行 rollup | 1775.473 | 1951.903 | +9.94% | 968.271 | 952.103 |

任务起始场景的三次回调 P95 均增加；回调活跃场景的三次分别增加10.04%、
19.01%、9.94%，因此两个场景均未通过回调不退化门槛。rollup 的平均耗时
及配对变化中位数均未退化，但不能据此忽略业务和回调的失败条件。

| 正式窗口内 API 受限周期比例 | A | B |
| --- | ---: | ---: |
| 无 rollup | 30.83% | 18.21% |
| 请求开始时运行 rollup | 28.53% | 15.60% |
| 回调活跃时运行 rollup | 25.35% | 14.37% |

API CPU 限流确实减少，但不能自动推导整体并发更好。PG 约102ms采样在正式
请求窗口内未观察到受限周期；不覆盖所有启动尖峰，也不证明生产 PG 可安全
减少配额。真实连接池等待已被单独记录，客户端及连接池超时均为0；本轮
没有调整池大小。样本只有三次配对，不声明统计显著性或真实用户容量。

## 停止范围与后续工作

不采用B配置，维持既有共享配置；本专项到此结束。停止追加CPU比例、池大小、
轮询策略和业务读取微调；保留此前独立验证、合并的基础优化。没有证据支持
仅为这几组延迟而删除额度、幂等、计量、必要清理或回调恢复等核心责任。

下一阶段只围绕真实业务闭环收集必要证据，不制造付费调用来证明性能。若
真实使用出现可复现的延迟、超时、积压或资源压力，另立有具体负载、目标、
预算和停止条件的任务；本轮10%判据不自动成为所有未来工作的统一标准。

M4 ARM、独立容器、500ms FakeProvider和模拟回调的结果不能替代2核4GB
