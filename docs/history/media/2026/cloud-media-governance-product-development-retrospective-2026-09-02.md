# Cloud 媒体治理产品与开发复盘 - 2026-09-02

Status: time-bounded media-governance historical synthesis; not implementation,
M4, production, or customer-acceptance evidence.

Current authority:
[Cloud Media Governance Standard](../../../cloud-media-governance-standard-v1.md)
and [Media Runtime Boundary](../../../media-runtime-boundary-v1.md).

本文归纳 2026-08-25 至 2026-09-02 围绕“媒体治理建议”的讨论历史，
将懂杯帝生产治理经验、产品边界、MVP 选择、恢复策略和开发方法集中记录。
它解释决策为什么形成，不证明相关 Cloud/Addon 功能已经完成、合并或被 M4
接受。

## 1. 讨论起点与事实基础

最初问题是：能否把一次成功的生产媒体库治理做成云端功能，并让用户通过
简单按钮完成复杂工作。

懂杯帝阶段治理提供了可量化的事实基础：

- 全媒体库约从 `40.56GB` 降至 `26GB`，减少约 `14.5GB`；
- 2022 年目录约从 `24GB` 降至 `15.4GB`；
- Web 日志约从 `18.9GB` 降至 `2.6GB`；
- 根分区最终约为 `41%`，可用空间约 `123GB`；
- 生产站没有因治理中断服务；
- 后期候选收益显著下降后主动停止，没有降低质量门槛凑处理数量。

这些数据说明价值不来自“转换了多少文件”，而来自在不中断生产的前提下，
可证明地识别占用、迁移引用、验证结果、释放空间并及时停止。

## 2. 决策如何演化

### 2.1 从压缩工具转向治理闭环

第一轮判断否定了“全部转 WebP”按钮。生产经验表明，真正的工作链是：

```text
容量审计 -> 引用审计 -> 风险分级 -> 离线转换 -> 收益与完整性验证
         -> 本地采用 -> 页面观察 -> 独立清理授权 -> 回滚或停止
```

关键纠偏包括：

- `uploads`、日志、备份和文件系统实际占用必须分开统计；
- “未匹配”只能表示证据不足，不能表示垃圾文件；
- 引用扫描不能只查正文，还要覆盖附件字段、postmeta、options、termmeta、
  usermeta、评论、主题/插件自定义表、REST 和动态路径；
- B2 的 `wp_termmeta.b2_tax_img` 成为“正文之外仍有真实引用”的代表案例；
- 转换完成与释放磁盘是两个不同动作；
- 总 404/5xx 没有路径关联时，不能直接归因于当前批次。

### 2.2 从“Cloud 全包”转向明确所有权

用户希望只点击一个按钮，把复杂工作交给云端。讨论最终形成的原则是：

> 简单体验可以由 Cloud 编排，但不能把 WordPress 真相和危险权限一起搬到
> Cloud。

Cloud 适合承担重计算和可观察工作：候选评分、离线转码、临时制品、哈希与
格式验证、收益判断、批次状态和停止证据。

WordPress/Addon 继续拥有引用真相、本地权限、审批、最终文件切换、附件与
数据库更新、缓存清理、回滚和删除。Cloud 不持有客户站点数据库、SSH 或
root 凭据，也不把下载成功或 delivery ACK 解释为本地已发布。

### 2.3 从完整平台转向可逆 MVP

讨论曾覆盖容量仪表盘、GIF、自动清理、Recovery Vault、多站点和完整任务
系统。随后按照“先看效果，再决定是否深入”的目标收敛为：

- 单站点；
- 只读审计；
- 仅静态 JPG/PNG，默认大于 `500KB`；
- 最低节省比例 `15%`，输出变大直接跳过；
- 先 `5-10` 个 canary，再考虑 `50-100` 个子批；
- Cloud 仅产出临时转换制品和证据；
- WordPress 本地审批采用；
- 保留生产原文件；
- 不处理 GIF、视频、未匹配文件或自动删除。

这不是缩减质量，而是选择最短的完整证据链。MVP 要同时证明安全性、实际
节省、运行稳定性和再次使用意愿；只证明编码器能输出 WebP 没有产品价值。

### 2.4 从“备份目录”转向分层恢复

恢复策略经历了三步澄清：

1. 同机保留 `30/90` 天可以帮助快速回滚，但不是灾难恢复；
2. 同一分区上的副本不会释放根分区空间，并可能加重容量压力；
3. 独立 OSS/S3 Recovery Vault 是删除生产原文件前的安全能力，但不是只读
   审计和 canary MVP 的前置条件。

因此最终顺序是：MVP 保留生产原文件并记录本地回滚清单；真实使用证明功能
值得继续后，再建设站点隔离、加密、版本化、可校验、可单文件恢复的异地
Recovery Vault。没有验证过的异地恢复来源时，生产原文件自动删除必须保持
禁用。

## 3. 可复用的开发方法

### 3.1 先列所有权，再画流程

跨 Cloud/WordPress 功能先回答四个问题：

1. 谁拥有输入事实；
2. 谁执行可重算工作；
3. 谁批准并执行不可逆写入；
4. 谁保留最终审计和恢复权。

这一步能防止“一键体验”演变成第二个 WordPress 控制面。

### 3.2 先盘点已有能力，再补合同缺口

现有 Media Runtime 已具备流式上传、静态图片任务、临时制品、站点绑定的
签名拉取、delivery ACK、TTL 和清理围栏；现有批次计划已具备本地枚举、
分块预览和 Core 审批方向。

需要新增的是治理语义，而不是第二套基础设施：

- `inventory_snapshot`；
- `reference_evidence`；
- `optimization_candidate`；
- `conversion_attempt`；
- `adoption_evidence`；
- `cleanup_proposal` / `stop_decision`。

每个候选应绑定 `scan_revision + source_sha256`。文件或引用状态变化后旧候选
立即失效，不能继续使用旧清单发布。

### 3.3 用状态链阻止证据越级

实现和界面都应区分：

```text
已审计 != 符合转换条件 != 已转换 != 已交付
       != 已批准 != 已采用 != 已观察 != 可清理 != 已清理
```

每一层只回答自己的问题。尤其不能把 Cloud 成功、文件下载成功、ACK 成功、
M4 candidate 或本地截图提升为 WordPress 已采用、`master` 已接受或生产已生效。

### 3.4 把危险动作拆成独立权限

用户可以通过一个主按钮启动治理，但内部至少保持三类事务：

- 转换：并发、低优先级、可重算；
- 本地采用：串行、幂等、逐项回滚；
- 清理：观察后独立授权，并要求可验证的异地恢复来源。

界面隐藏技术细节，不等于后端合并权限和失败域。

### 3.5 让停止成为正式产物

停止器应输出带理由的 `stop_decision`，至少考虑合格率、节省比例、剩余可
处理字节、验证失败率、引用覆盖缺口、磁盘压力和单位释放成本。

本次生产经验中，225 个 GIF 候选最终 `0` 个符合发布要求，是停止并推迟 GIF
能力的依据。连续代表性批次低收益时，应停止或只报告，不能降低 `15%` 门槛
制造成功数字。

### 3.6 用试点证据决定基础设施投入

Recovery Vault、自动清理、多站点任务和动画处理都可能合理，但它们应由
试点结果触发，而不是因为完整架构图看起来需要。建议先观察 `1-2` 周、
`24-72` 小时稳定窗口、实际释放量、相关 404/5xx、回滚成功率、服务器负载、
操作者时间和重复使用意愿，再决定下一阶段。

## 4. 曾考虑但明确推迟的方向

| 方向 | 推迟原因 | 重新开启条件 |
| --- | --- | --- |
| GIF 自动治理 | 当前静态处理链不具备完整动画合同，生产样本收益为零 | 独立定义帧数、时长、循环、透明度和视觉验收合同 |
| 自动删除原文件 | 不可逆，且本地副本不是异地恢复 | Recovery Vault 可读、哈希完整、恢复演练通过、观察稳定、用户单独授权 |
| 视频/日志/备份治理 | 权限、工具和恢复模型与图片不同 | 独立产品合同和独立试点 |
| 全站一键发布 | 掩盖引用覆盖、失败域和回滚状态 | canary 与小批次长期稳定，并保留阶段化授权 |
| 第二任务引擎 | 现有 FastAPI/Postgres/Redis/worker 已覆盖运行基础 | 只有经测量的现有运行时瓶颈才能重新评估 |
| 完整媒体控制台 | MVP 尚未证明重复使用和商业价值 | 真实用户反馈、重复使用或明确运营需求 |

## 5. 下一阶段开发检查表

开始实现前：

- [ ] 冻结 Cloud/WordPress 所有权和禁止字段；
- [ ] 盘点并复用现有 Media Runtime、批次计划和 Addon proposal seam；
- [ ] 冻结版本化的 inventory、reference、candidate、attempt 和 stop schemas；
- [ ] 建立包含 B2 termmeta、动态引用、未匹配文件和过期候选的固定测试夹具；
- [ ] 声明单站点、JPG/PNG、canary、无删除的明确非目标。

实现时：

- [ ] 只读审计路径产生零 WordPress 写入；
- [ ] 真实格式、解码、尺寸、SHA-256 和 MIME 都经过验证；
- [ ] `scan_revision` 或源哈希变化使候选失效；
- [ ] Cloud 结果只投射建议和证据，不出现本地批准/发布字段；
- [ ] 本地采用串行、幂等、按附件回滚；
- [ ] 低收益和验证失败会生成停止证据；
- [ ] 没有异地恢复时清理入口始终禁用。

验收时：

- [ ] canary 相关图片 404 为零；
- [ ] 页面、REST、HTTPS MIME 和附件 metadata 一致；
- [ ] 注入单项失败不会回滚无关附件；
- [ ] Cloud 转换、交付、本地采用和观察状态没有互相代替；
- [ ] 报告 local、PR/merge、M4 candidate、M4 accepted、production 和 human
      evidence 的真实层级；
- [ ] 若价值或安全证据不足，记录 `stop`，不扩展范围。

## 6. 本轮证据边界

截至本记录日期，对话已经形成并写入现行标准的产品和架构方向；历史任务中
还出现过 Cloud 与 Addon 实现分支、候选提交和继续收尾的交接信息，但引用任务
最终处于系统错误状态，没有在该对话内形成可核验的完整 PR、required checks、
合并、clean-`master` M4 promotion 或生产证据。

因此可以声称：

- 生产治理事实和经验已经归纳；
- Cloud/WordPress 边界、MVP、恢复和停止策略已经形成；
- 现行媒体治理标准已存在并可指导后续实现。

不能据此声称：

- 媒体治理 MVP 已完成；
- Cloud/Addon 跨仓合同已被当前主线接受；
- M4 或生产环境已经验证该功能；
- 真实用户已确认该产品值得继续扩展。

后续实现必须重新核对当前 `origin/master`、Addon 主线、现有分支和实际测试，
不能把本历史记录中的工作树、提交或候选状态当作当前事实。

## 7. 总结

这段讨论最重要的开发经验不是某组 WebP 参数，而是以下顺序：

```text
先证明空间在哪里，
再证明文件是什么、谁在使用，
然后证明转换确实安全且有收益，
再由 WordPress 本地批准采用，
观察稳定并证明可恢复后，最后才讨论删除。
```

产品层面可以保持“一键启动”；工程层面必须保留证据、权限、状态、回滚和
停止边界。最小版本的目标不是覆盖所有媒体，而是用一个可逆的静态图片垂直
切片回答：这项能力是否安全、是否节省、是否有人愿意再次使用。
