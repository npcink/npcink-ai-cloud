## 3. 收益与决策

目前没有收集到足够证据证明上述长度正在持续造成故障或显著拖慢交付，收益无法量化。
不启动全仓重构项目，优先核心 WordPress 使用闭环和真实问题修复。

主要收益是未来维护成本降低，不能直接承诺用户体验或运行性能改善。全仓同时拆分会
增加 characterization、迁移、评审和验证成本。Runtime 潜在收益较高，但涉及计费、
队列和失败恢复，不能据此认定最适合立即动手。

具体需求触发时，Service 中一个独立纯读投影可以作为候选。这是相对低风险的起点，
不是立即实施的承诺；保留返回、权限和错误合同，先测试再移动，结构与业务变化分开。

重新启动的信号：反复回归、小需求跨多个不相关职责、测试难以隔离并拖慢反馈，或
新功能被迫复制业务规则。届时记录具体证据，再选一个热点和可回滚的短批次。

## 4. 开发经验

1. 先确认审查已有改动还是盘点现有结构；没有代码差异时，不把盘点称为 diff 审查。
2. 行数用于定位，职责、依赖和真实变更成本用于决策，数据文件与业务模块分开判断。
3. 检查拆分后的独立性；mixin 和页面组件仍可能共享大量隐式状态。
4. 保留有用的现有拆分与薄装配层，边际收益不足时主动暂停。
5. 推荐技术起点时同时说明是否值得现在投入，避免候选排序被误读为项目建议。
6. 区分源码观察、测试存在、测试通过、M4 验证和实际用户收益，不跨证据层级下结论。

通用决策规则已补入现行结构整改交付标准第 3.1 节；具体需求的实施和验证在对应任务
记录，不持续改写本文的历史快照。
