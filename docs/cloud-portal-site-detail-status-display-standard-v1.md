# Cloud Portal 站点详情状态与告警展示规范 v1

Status: active engineering and product standard.

Purpose: 约束 Portal 站点详情页的状态归属、告警文案、操作入口和验证方式，避免把一个模块的提醒错误展示为另一个模块的故障。

Scope: `frontend/src/app/portal/sites/[siteId]/page.tsx`、站点服务状态、站点知识摘要，以及为这些页面提供状态分类的展示辅助函数。

This document supplements [Cloud Portal Customer Workspace UI Standard](cloud-portal-customer-workspace-ui-standard-v1.md). It does not change Cloud API ownership, WordPress control-plane ownership, indexing lifecycle, or billing rules.

## 1. Problem And Root Cause

站点详情页曾经同时出现“已接入”“服务需要关注”和“知识库需要关注”。但页面中的明确错误数为 0、用量正常，用户无法判断是否需要处理。

根因不是单一文案错误，而是状态聚合和展示映射同时缺少边界：

1. Cloud 监控摘要把连接、运行、媒体、站点知识、额度等不同领域放在同一个总健康值中。
2. Portal 站点页直接把总健康值映射成服务状态和顶部告警。
3. 知识库提醒没有单独的展示分类，因而可能被当作连接或服务故障。
4. 正常状态仍展示刷新按钮和完整检查表，放大了用户对“需要维护”的感受。

结论：不能用一个通用的 `needs_attention` 或总健康值驱动整页 UI。必须先按状态归属分类，再决定页面级告警和操作。

## 2. State Ownership

| 状态领域 | 用户可见名称 | 负责回答的问题 | 是否可触发顶部告警 |
| --- | --- | --- | --- |
| Connection lifecycle | 接入状态 | WordPress 站点是否已接入 | 可以 |
| Service operation | 服务状态 | Cloud 服务是否存在影响使用的问题 | 可以 |
| Site Knowledge | 站点知识 | 页面内容是否已收录、最近是否更新 | 不直接触发服务告警 |
| Capacity | 用量/容量 | 当前套餐是否接近或超过限制 | 可以，但必须指向套餐处理 |

规则：

- `已接入` 只代表连接生命周期，不代表服务健康或知识库完成。
- 站点知识的无命中、更新延迟或索引提醒只能显示在“站点知识”区域。
- 容量问题必须链接到套餐或用量处理，不得显示成连接故障。
- 数据请求失败、状态过期和真实业务异常必须区分，不能都显示为“需要关注”。

## 3. Page Hierarchy

站点详情页按以下顺序组织：

```text
站点身份与接入状态
  -> 只有存在真实影响时显示一条具体告警
  -> 服务状态摘要
  -> 站点知识摘要
  -> 低频的移除等危险操作
```

### 3.1 Header

顶部默认只显示：

- 站点名称；
- `已接入` 等接入生命周期状态；
- 网站地址；
- 最近活动时间。

顶部告警必须同时满足：

1. 问题属于连接、服务运行或容量领域；
2. 有明确证据支持；
3. 能给出一个最佳下一步。

告警标题必须描述对象和条件，例如 `知识库更新失败`、`站点容量已超限`，禁止只显示 `需要关注`。

### 3.2 Service Status

服务正常时只显示一条结论：

> 服务正常，最近检查未发现影响使用的问题。

正常状态不显示完整监控表，也不显示刷新按钮。

只有以下情况才显示详细检查项或“重新检查”：

- 服务请求加载失败；
- 连接失效；
- 服务运行明确报错；
- 容量确实需要处理。

“明确错误事件 0”可以作为异常详情的证据，但不能与一个无来源的“服务需要关注”并列制造矛盾。

### 3.3 Site Knowledge

站点知识区域默认回答三个问题：

1. 已收录多少页面；
2. 最近什么时候更新；
3. 是否被使用。

默认文案应明确自动行为：

> 内容变化后会自动更新。

允许的用户状态：

| 内部条件 | 默认文案 | 默认操作 |
| --- | --- | --- |
| 尚无收录内容 | 尚未开始 | 无；等待站点接入和自动更新 |
| 已收录且正常 | 知识库正常 | 无 |
| 状态暂不完整或过期 | 待确认 | 仅在确有必要时重新检查 |
| 更新请求明确失败 | 更新失败 | 重新检查 |

知识库正常时不得展示手动同步或刷新入口。索引生命周期和自动更新仍由 Cloud 与插件既有契约负责，Portal 只展示结果摘要。

## 4. Status Classification Contract

所有 Portal 页面级判断必须先经过展示分类函数，再渲染文案或操作。当前约定的分类为：

- `connection`
- `service`
- `knowledge`
- `quota`

实现要求：

1. 知识库相关的 `vector`、`knowledge`、`site_search` 证据归入 `knowledge`。
2. `knowledge` 不得参与服务运行状态的错误或警告计算。
3. `quota` 不得参与连接状态计算。
4. 页面顶部只消费连接、服务和容量分类的聚合结果。
5. 同一个分类函数同时服务顶部告警、服务状态和附加事项列表，避免不同区域各自猜测状态。

禁止：

- 直接使用 `overview.health.status` 作为整页告警；
- 用 `action_required.length > 0` 判断站点连接异常；
- 用总健康分数决定知识库文案；
- 让正常状态渲染无操作的刷新、重试或“查看详情”按钮。

## 5. Action Rules

每个状态最多有一个最佳下一步：

| 状态 | 首选动作 |
| --- | --- |
| 连接失效 | 从 WordPress 插件重新接入 |
| 服务明确异常 | 重新检查；持续异常时提交工单 |
| 容量接近或超限 | 查看套餐 |
| 知识库更新失败 | 重新检查 |
| 正常 | 不显示操作 |

不要在顶部、服务卡和知识库卡重复放置同一个动作。低频危险操作（例如移除站点）继续放在“其他操作”折叠区域。

## 6. Required Test Matrix

每次调整状态聚合或站点详情页面时，至少验证以下场景：

| 场景 | 服务状态 | 顶部告警 | 知识库状态 | 刷新入口 |
| --- | --- | --- | --- | --- |
| 全部正常 | 正常 | 无 | 知识库正常 | 无 |
| 只有知识库提醒 | 正常 | 无 | 待确认 | 默认无 |
| 只有额度压力 | 待确认/异常 | 容量具体告警 | 不变 | 查看套餐 |
| 连接凭证失效 | 异常 | 连接具体告警 | 不变 | 重新检查/重新接入 |
| 知识库请求失败 | 不改变服务状态 | 无 | 更新失败 | 重新检查 |
| 所有请求加载失败 | 待确认 | 明确说明无法加载 | 待确认 | 重试 |

至少应有一个单元测试锁定“只有知识库警告时服务状态仍为正常”。页面契约还应检查正常状态不渲染重复刷新入口。

## 7. Review Checklist

提交 Portal 站点详情页变更前，逐项确认：

- [ ] 接入状态、服务状态、知识库状态和容量状态没有混用。
- [ ] 顶部告警包含具体对象、具体条件和一个下一步。
- [ ] 正常状态没有泛化的“需要关注”。
- [ ] 正常状态没有无意义的刷新或重试按钮。
- [ ] 知识库文案说明内容变化会自动更新。
- [ ] 知识库异常不会改变服务运行状态。
- [ ] 容量问题指向套餐，而不是提交连接工单。
- [ ] 页面默认只展示用户能采取行动的内容，技术详情留在低频入口或 Cloud 运营面。
- [ ] 已覆盖“只有知识库异常”和“全部正常”两个最容易回归的场景。

## 8. Remediation Record

本规范由 2026-08-25 的 Portal 站点详情页整改形成。对应实现包括：

- `getPortalMonitoringIssueCategory()` 增加知识库分类；
- `getPortalServiceOperationStatus()` 排除知识库和额度对服务运行的错误归因；
- 站点详情页顶部告警只消费服务相关分类；
- 正常服务和正常知识库隐藏刷新入口；
- 增加状态分类单元测试及 Portal 页面契约验证。

本规范不授权新增 Cloud API、WordPress 写操作、知识库生命周期控制或本地第二套索引真相。
