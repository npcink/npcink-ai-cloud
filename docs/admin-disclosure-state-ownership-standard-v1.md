# Admin Disclosure 状态所有权规范 v1

状态：已确认，源自 Usage Statistics / Editorial Outcomes 改造。

## 目的

避免一个 Admin 区域同时由外层 React 状态和内层 `<details>` 控制，导致按钮、
内容和加载状态互相矛盾。

## 规则

1. 一个可展开事实只能有一个状态所有者。
2. `mounted`、`loaded`、`open`、`expanded` 是不同事实，必须分别命名；不得
   用其中一个事实隐式代表另一个事实。
3. 如果父组件控制“点击后加载”，子组件必须提供无 disclosure 模式：父组件
   打开时内容直接可见，不能要求用户二次点击。
4. 如果子组件使用原生 `<details>`，父组件不得再提供同一内容的展开按钮。
5. 按钮的 `aria-expanded` 必须和实际可见内容同步；展开按钮显示“收起”时，
   目标内容必须已经可见。
6. 低频内容可以延迟挂载或延迟请求，但延迟加载完成后不应再次隐藏在第二层
   未同步的 disclosure 后面。

## 推荐实现

二选一：

- 父控模式：父组件控制挂载和展开，子组件是直接渲染内容的纯工作区；
- 子控模式：子组件完整拥有 `<details>` 和打开状态，父组件只负责挂载。

不要混用两种模式。复用组件确实需要两种行为时，使用显式的
`disclosure`/`controlled` API，并在调用点写明模式。

## 自动化验收

每个 material Admin disclosure 至少验证：

- 初始折叠时目标内容不存在或不可见；
- 点击后按钮 `aria-expanded=true`；
- 点击后目标内容可见；
- 不存在需要二次点击才能显示内容的嵌套 disclosure；
- 再次点击后内容收起；
- 低频请求只在授权展开后发起。

视觉门禁还应检查展开前后的高度变化、异常空白、横向溢出和重复标题。

## 异常处置工作台扩展规则

异常列表应同时表达四件事：严重性、影响范围、证据边界和建议处理角色。排序
至少先按严重性，再按影响次数；当数据不足时必须保留“样本有限/证据缺失”
提示，不能把缺失记录当成失败数量。

异常详情应提供一个明确的下一步动作，并标明建议处理角色。推荐角色包括
Cloud 平台管理员、技术支持人员和程序维护人员。跳转可以进入只读证据或配置
页面，但不得因为查看诊断而自动修改设置。

对 Provider 调用缺口、计量缺口、Provider 错误和运行失败，必须使用不同的
结论文案。完整率、失败数、运行数和时间窗口分别表示不同事实，不能合并成一
个“健康率”替代这些证据。
