# 开发会话操作经验记录（2026-09-22）

Status: dated development experience record. 记录 2026-09-21/22 战略文档会话中
可复用的流程经验，供后续 AI 会话与操作者参考；本文是经验记录，不是新的强制
标准（现行权威仍是操作模型、验证分层与各仓 AGENTS.md）。

## 1. docs-only 任务的标准路径（本轮反复验证）

锁定工作树 → 写文档 → 门禁组合（`git diff --check`、
`bash scripts/check-release-policy.sh`、相对链接逐一 `test -f`、
`check:changed -- --plan`）→ 以 `git -C <worktree>` 形式提交 → 从
`.github/pull_request_template.md` 起草 PR 正文（未跑的检查如实标注"未跑"）→
发布 → 确认 MERGED → 解锁并移除工作树。

## 2. master 高频移动时的发布纪律

多会话并行时 master 每小时可能多次前移；发布器要求分支包含最新
origin/master——**发布前一律 fetch + rebase**，变基后重跑链接检查（docs
索引锚点可能漂移）。长链命令中的 `tail` 会吞掉发布器真实错误（典型如
"branch must include the latest origin/master"），排障时去掉管道再看全文。

## 3. 子智能体全流程模式（已验证可行）

- 一般代理可独立完成"工作树 → 文档 → 门禁 → PR → 合并 → 清理"全流程，
  前提是提示词自包含：精确命令形式、PR 正文要点、硬性边界、返回格式；
- 调查类任务先用只读 Explore 代理，主会话核实关键论断后再由执行代理落档
  （本轮修正过两处失真：一篇文档的所属仓库归属、一个配置项的命名前缀）；
- 多个 docs 任务会争抢 `docs/README.md` 索引，必须**串行发布**；
- 给子代理的测量类任务尽量由主会话先完成采集、把数字写进提示词，代理只
  落档（凭据留在主会话，不入提示词与文档）。

## 4. Mimosa 预提交门禁的两个事实（2026-09-21/22 记录）

- 拦截按 Bash 命令文本匹配 `git commit`，`--no-verify` 无效（git 从未执行，
  整条命令被前置阻断）；
- 无按次豁免开关；存量测试假键（如 `api_key="test-api-key"` 桩值）是误报
  来源。操作者已在其他会话处理；再遇拦截时先区分"本任务引入"与"存量误报"。

## 5. 其他操作坑

- 并行工具调用有时序风险：依赖新工作树存在的 Read 必须等工作树创建命令
  返回后再发（本轮撞过一次空读）；
- `gh` 在 detached HEAD 的主工作树下无法推断分支，需显式 `--repo` + PR 号；
- 工作树里 `cd` 后删除该工作树，后续命令会因 cwd 失效报错——清理动作放在
  主仓路径下执行。

## 6. 会话边界原则的执行经验

"只管本会话内容"的落地方式：不读写其他会话的工作树与分支；需要集成他人在
途成果时，从其提交点新建本会话分支 + 工作树变基合入（PR #985 先例），原
工作树与分支留给属主会话或操作者清理。

## 7. squash 合并与分支判定

本仓 PR 均为 squash 合并：合并产生新提交，原分支提交不再构成 master 的
祖先，`git branch --merged` 与 `merge-base --is-ancestor` 都无法判定集成
状态。判定已集成只能以"PR MERGED + merge commit"为准（AGENTS.md 已有此
规则），据此清理分支时需逐分支核对合并 PR 后再删。
